# Уровни изоляции

Почему два запроса в одной транзакции могут увидеть разное количество строк, и как запретить это на уровне базы?

Уровень изоляции определяет, насколько транзакция защищена от изменений, которые делают другие транзакции одновременно. Чем выше уровень, тем меньше аномалий, но больше блокировок, откатов и сложнее производительность. В PostgreSQL есть три практических уровня: `READ COMMITTED`, `REPEATABLE READ` и `SERIALIZABLE`.

## Уровни

| Уровень | Что видит транзакция | Когда использовать |
| --- | --- | --- |
| `READ COMMITTED` | только зафиксированные данные на момент каждой команды | по умолчанию, большинство случаев |
| `REPEATABLE READ` | снимок данных на момент начала транзакции | отчёты, несколько согласованных чтений |
| `SERIALIZABLE` | как будто транзакции выполнялись по очереди | критичные расчёты, деньги, остатки |

`READ UNCOMMITTED` в PostgreSQL фактически работает как `READ COMMITTED`: грязное чтение не допускается.

## Синтаксис

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT COUNT(*) FROM orders WHERE status = 'paid';

-- другие транзакции могут добавлять заказы,
-- но этот запрос увидит тот же снимок
SELECT COUNT(*) FROM orders WHERE status = 'paid';

COMMIT;
```

Уровень задаётся на транзакцию. Можно указать его сразу:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
```

## Пример: отчёт

Бухгалтер строит отчёт из нескольких запросов: сначала сумма заказов, потом количество позиций. На `READ COMMITTED` между запросами кто-то может добавить заказ, и цифры разойдутся.

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT SUM(total) FROM orders WHERE status = 'paid';
SELECT COUNT(*) FROM order_items;

COMMIT;
```

Оба запроса увидят один и тот же снимок. Отчёт будет внутренне согласован.

## SERIALIZABLE и откаты

`SERIALIZABLE` может откатить транзакцию с ошибкой `could not serialize access due to concurrent update`. Это не баг, а цена гарантии: приложение должно повторить транзакцию.

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ...
COMMIT;
```

Если поймал ошибку сериализации — повтори всю транзакцию, а не отдельную команду.

## Грабли

* **`REPEATABLE READ` не блокирует всё.** Другие транзакции могут менять данные; ты просто не увидишь их изменения до конца своей транзакции.
* **`SERIALIZABLE` требует retry.** Без повторной попытки приложение будет падать на конфликтах.
* **Уровень не отменяет логику.** Даже `SERIALIZABLE` не спасёт от неправильной формулы.
* **Долгая транзакция на высоком уровне.** Больше конфликтов и откатов, особенно при массовых записях.
* **`SET TRANSACTION` до первой команды.** После начала работы менять уровень нельзя.
* **Разные СУБД — разные детали.** В MySQL уровни и поведение отличаются; не переноси настройки вслепую.
