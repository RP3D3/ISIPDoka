# Оптимистичная и пессимистичная блокировка

Когда лучше заблокировать строку заранее, а когда — просто проверить версию и повторить попытку при конфликте?

Два подхода к конкурентному изменению данных. **Пессимистичная блокировка** предполагает, что конфликт будет, и заранее блокирует строку через `SELECT ... FOR UPDATE`. **Оптимистичная** предполагает, что конфликт редок: читаем версию, меняем данные и при записи проверяем, что версия не изменилась.

## Пессимистичная блокировка

```sql
BEGIN;

SELECT stock
FROM ingredients
WHERE id = 1
FOR UPDATE;

-- пока транзакция открыта, другие ждут
UPDATE ingredients
SET stock = stock - 1
WHERE id = 1;

COMMIT;
```

Плюс: просто и надёжно, второй писатель ждёт. Минус: блокировка держится всё время транзакции, а при долгих операциях мешает другим.

## Оптимистичная блокировка

Добавим столбец версии:

```sql
ALTER TABLE ingredients ADD COLUMN version INT NOT NULL DEFAULT 0;
```

Чтение:

```sql
SELECT id, stock, version
FROM ingredients
WHERE id = 1;
-- stock = 10, version = 7
```

Запись:

```sql
UPDATE ingredients
SET stock = stock - 1,
    version = version + 1
WHERE id = 1
  AND version = 7;
```

Если `UPDATE` затронул `0` строк, значит, кто-то уже изменил строку. Приложение читает заново и повторяет.

```text
UPDATE 0
```

## Сравнение

| Критерий | Пессимистичная | Оптимистичная |
| --- | --- | --- |
| Блокировка | сразу и до `COMMIT` | нет, проверка при записи |
| Конфликты | ждут | получают retry |
| Хороша при | частых конфликтах | редких конфликтах |
| Сложность | ниже | нужен цикл повторов |
| Долгие операции | мешает другим | не блокирует |

## Пример: остаток на складе

Остаток меняется часто и должен быть точным — пессимистичная блокировка или атомарный `UPDATE`:

```sql
UPDATE ingredients
SET stock = stock - 1
WHERE id = 1 AND stock > 0
RETURNING stock;
```

Профиль клиента меняется редко — оптимистичная:

```sql
UPDATE customers
SET name = 'Анна П.',
    version = version + 1
WHERE id = 1 AND version = 3;
```

## Грабли

* **Забыть проверить число строк.** `UPDATE` с версией вернёт `0`, но приложение может этого не заметить и показать успех.
* **Версия не увеличивается.** Тогда проверка бессмысленна: конфликт не будет обнаружен.
* **Долгая пессимистичная транзакция.** Блокировка на время внешнего запроса или ожидания пользователя — плохая идея.
* **Retry без ограничения.** Бесконечные повторы при высокой конкуренции. Ограничь число попыток и добавь задержку.
* **Смешивание подходов.** Если часть кода блокирует строку, а часть проверяет версию, договорись о едином правиле.
* **Оптимистичная блокировка не для остатков.** При высокой конкуренции слишком много retry; лучше атомарный `UPDATE` или `FOR UPDATE`.
