# Аномалии

Как два кассира одновременно продают последний круассан, хотя каждый видел остаток `1`, и кто в итоге виноват?

Аномалия — это ситуация, когда параллельные транзакции дают результат, невозможный при последовательном выполнении. Уровни изоляции как раз ограничивают такие ситуации. Важно узнавать аномалии в лицо: иначе они выглядят как «случайный баг», который не воспроизводится.

## Основные аномалии

| Аномалия | Что происходит | Пример |
| --- | --- | --- |
| Грязное чтение | видно незафиксированные изменения | чужой `UPDATE` ещё не `COMMIT` |
| Неповторяющееся чтение | повторный `SELECT` вернул другое значение | цена изменилась между запросами |
| Фантом | повторный `SELECT` вернул новые строки | добавили заказ в диапазон |
| Потерянное обновление | два `UPDATE` перезаписали друг друга | остаток списан один раз вместо двух |

## Пример: потерянное обновление

Остаток круассанов — `1`. Два кассира одновременно читают `1`, каждый вычитает `1` и записывает `0`.

```sql
-- кассир 1
BEGIN;
SELECT stock FROM ingredients WHERE name = 'круассан';  -- 1
UPDATE ingredients SET stock = 0 WHERE name = 'круассан';
COMMIT;

-- кассир 2 (параллельно)
BEGIN;
SELECT stock FROM ingredients WHERE name = 'круассан';  -- тоже 1
UPDATE ingredients SET stock = 0 WHERE name = 'круассан';
COMMIT;
```

Продали два круассана, а остаток стал `0`, а не `-1`. Одно обновление потерялось.

## Как исправить

**Атомарный `UPDATE`:**

```sql
UPDATE ingredients
SET stock = stock - 1
WHERE name = 'круассан'
  AND stock > 0
RETURNING stock;
```

Если строк не вернулось — товара нет. База сама сериализует обновление строки.

**Блокировка строки:**

```sql
SELECT stock
FROM ingredients
WHERE name = 'круассан'
FOR UPDATE;
```

`FOR UPDATE` блокирует строку до конца транзакции. Второй кассир подождёт.

**Проверка версии (оптимистичная блокировка):**

```sql
UPDATE ingredients
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 7;
```

Если `UPDATE` затронул `0` строк, данные изменились — читай заново и повторяй.

## Уровни и аномалии

| Аномалия | `READ COMMITTED` | `REPEATABLE READ` | `SERIALIZABLE` |
| --- | --- | --- | --- |
| Грязное чтение | нет | нет | нет |
| Неповторяющееся чтение | возможно | нет | нет |
| Фантом | возможно | нет | нет |
| Потерянное обновление | возможно | возможно* | нет |

\* В PostgreSQL `REPEATABLE READ` обнаруживает конфликт обновлений и откатывает одну из транзакций, но не все СУБД ведут себя так.

## Грабли

* **«У нас же PostgreSQL».** Даже он не спасёт от логики «прочитал, посчитал в приложении, записал».
* **Проверка перед `UPDATE`.** `SELECT` и следующий `UPDATE` — не атомарны без блокировки.
* **`SERIALIZABLE` без retry.** Конфликты будут, и приложение должно повторять транзакцию.
* **Долгие транзакции.** Чем дольше открыта, тем больше окно для конфликтов.
* **Аномалии в отчётах.** Отчёт из нескольких запросов на `READ COMMITTED` может быть внутренне противоречивым.
