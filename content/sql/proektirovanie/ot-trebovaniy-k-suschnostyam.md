# От требований к сущностям

Как из описания бизнеса выделить таблицы, не превратив всё в одну свалку с сотней столбцов?

Сущность — это объект, о котором нужно хранить данные: клиент, заказ, напиток. Связь — отношение между сущностями: клиент делает заказы, заказ содержит напитки. Проектирование начинается с существительных и глаголов в требованиях, а не с `CREATE TABLE`.

## Шаг 1. Выделить существительные

Требование: «Клиент заказывает напитки, мы доставляем по адресам, хотим видеть историю и отзывы».

Существительные-кандидаты:

- клиент → `customers`
- заказ → `orders`
- напиток → `drinks`
- адрес → `addresses`
- отзыв → `reviews`

Не каждое существительное становится таблицей. «История» — это, скорее, свойство заказов, а не отдельная сущность.

## Шаг 2. Определить кардинальность

| Связь | Тип | Реализация |
| --- | --- | --- |
| клиент — заказы | 1:N | `orders.customer_id` |
| заказ — позиции | 1:N | `order_items.order_id` |
| напиток — позиции | 1:N | `order_items.drink_id` |
| клиент — адреса | 1:N | `addresses.customer_id` |
| заказ — напитки | M:N | через `order_items` |

Связь «многие ко многим» почти всегда требует промежуточной таблицы.

## Шаг 3. Проверить атрибуты

Для каждой сущности выпиши, что о ней известно:

```text
customers: имя, телефон, email, дата регистрации
orders: клиент, дата, статус, сумма
drinks: название, категория, цена, активен ли
order_items: заказ, напиток, количество, цена на момент заказа
```

Цена в `order_items` хранится отдельно от `drinks.price`: цена напитка может измениться, а история заказа должна остаться прежней.

## Шаг 4. Проверить правила

- Email клиента уникален?
- Цена не может быть отрицательной?
- Заказ не может существовать без клиента?
- Позиция не может быть без заказа?

Эти правила станут `UNIQUE`, `CHECK`, `NOT NULL` и внешними ключами.

## Пример

```sql
CREATE TABLE customers (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(id),
    status TEXT NOT NULL DEFAULT 'new'
        CHECK (status IN ('new', 'paid', 'done', 'cancelled')),
    total NUMERIC(10, 2) NOT NULL DEFAULT 0 CHECK (total >= 0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## Грабли

* **Одна таблица на всё.** «Заказы» с полями клиента, адреса и напитков превращаются в дубли.
* **Пропущенная связь M:N.** Без промежуточной таблицы появляются списки в строке или дубли.
* **Атрибут не той сущности.** Цена напитка и цена в заказе — разные факты.
* **Слишком ранняя оптимизация.** Сначала модель, потом индексы и денормализация.
* **Нет ограничений.** Схема без `NOT NULL` и внешних ключей быстро заполняется мусором.
* **Имена-загадки.** `t1`, `data`, `value` через месяц не поймёт никто.
