# Когда денормализовать

Когда дублирование данных оправдано, а когда это просто способ создать себе проблему на будущее?

Денормализация — это осознанное добавление избыточности: дублирование столбца, хранение агрегата или объединение таблиц. Она ускоряет чтение, но усложняет запись и требует синхронизации. Нормализация — правило по умолчанию, денормализация — исключение с причиной.

## Когда оправдано

- **Тяжёлые отчёты.** Суммы и агрегаты считаются редко, читаются часто.
- **Исторические снимки.** Цена на момент заказа хранится в `order_items`, даже если есть `drinks.price`.
- **Внешние системы.** Данные из API удобно хранить в `JSONB`.
- **Очень частые чтения.** Например, счётчик заказов клиента.
- **Материализованные представления.** Результат запроса хранится отдельно.

## Пример: историческая цена

```sql
CREATE TABLE order_items (
    order_id BIGINT REFERENCES orders(id),
    drink_id BIGINT REFERENCES drinks(id),
    quantity INT NOT NULL,
    unit_price NUMERIC(10, 2) NOT NULL,
    PRIMARY KEY (order_id, drink_id)
);
```

`unit_price` дублирует `drinks.price`, но это не ошибка: цена меняется, а история заказа должна остаться прежней.

## Пример: агрегат

```sql
ALTER TABLE customers ADD COLUMN orders_count INT NOT NULL DEFAULT 0;
```

Обновлять его нужно при создании и удалении заказа:

```sql
UPDATE customers
SET orders_count = orders_count + 1
WHERE id = 1;
```

Или пересчитывать:

```sql
UPDATE customers AS c
SET orders_count = (
    SELECT COUNT(*) FROM orders WHERE customer_id = c.id
);
```

## Цена денормализации

| Плюс | Минус |
| --- | --- |
| быстрое чтение | сложнее запись |
| меньше `JOIN` | риск рассинхронизации |
| простые отчёты | нужны триггеры или фоновая синхронизация |

## Правило

Сначала нормализуй. Денормализуй, когда:

1. Есть измеренная проблема производительности.
2. Есть способ поддерживать согласованность.
3. Есть тест, который ловит расхождение.

## Грабли

* **Денормализация «на всякий случай».** Лишние столбцы и триггеры без выигрыша.
* **Забыть синхронизацию.** Агрегат обновили в одном месте, а в другом — нет.
* **Дублировать изменяемые данные.** Название категории в каждой строке — плохой кандидат.
* **Считать, что `JOIN` всегда медленный.** Современные базы хорошо соединяют по индексам.
* **Нет метрики.** Без замера нельзя понять, помогло ли.
* **Денормализация вместо индекса.** Часто проблема решается индексом, а не дублем.
