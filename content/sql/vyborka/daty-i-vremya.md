# Даты и время

Как найти заказы за последние семь дней и не попалиться на часовых поясах, границах суток и форматах?

Даты — самый частый источник тихих ошибок. «За сегодня» в Москве и в UTC — разные интервалы. `BETWEEN` по датам не включает последний день целиком. `now()` возвращает момент начала транзакции, а не текущую секунду. В PostgreSQL есть три типа для времени, и путать их дорого.

## Три типа

| Тип | Что хранит | Когда использовать |
| --- | --- | --- |
| `DATE` | только дату | день рождения, календарный день |
| `TIMESTAMP` | дату и время без пояса | «местное» время, если пояс не важен |
| `TIMESTAMPTZ` | момент времени с поясом | события: заказы, платежи, логи |

`TIMESTAMPTZ` хранит момент в UTC, а показывает его в поясе сессии. Поэтому заказ, сделанный в 10:00 в Москве, будет тем же моментом, что и 07:00 в UTC.

## Синтаксис

```sql
SELECT ...
FROM ...
WHERE created_at >= now() - interval '7 days';
```

| Функция | Что делает |
| --- | --- |
| `now()` | текущий момент времени |
| `CURRENT_DATE` | текущая дата |
| `date_trunc('day', created_at)` | обрезает время до начала дня |
| `extract(hour FROM created_at)` | достаёт часы, день, месяц |
| `created_at + interval '1 day'` | прибавляет интервал |
| `age(now(), created_at)` | разница между моментами |

## Пример

Заказы за последние три дня:

```sql
SELECT id, created_at, total
FROM orders
WHERE created_at >= now() - interval '3 days'
ORDER BY created_at DESC;
```

Если сейчас 15 мая 2026, 12:00, в результат попадут заказы начиная с 12 мая 12:00:

| id | created_at | total |
| --- | --- | --- |
| 128 | 2026-05-14 10:15+03 | 640.00 |
| 127 | 2026-05-14 09:40+03 | 280.00 |
| 126 | 2026-05-13 18:05+03 | 410.00 |
| 125 | 2026-05-13 12:30+03 | 320.00 |
| 124 | 2026-05-12 16:20+03 | 500.00 |

Заказ 123 от 12 мая 08:10 не попал: он раньше границы.

## Границы суток

Чтобы взять все заказы за 13 мая, не полагайся на `BETWEEN` с датами. Надёжнее полуоткрытый интервал:

```sql
WHERE created_at >= '2026-05-13'
  AND created_at <  '2026-05-14'
```

Левая граница включается, правая — нет. Такой запрос корректно работает и с `TIMESTAMPTZ`, и с `TIMESTAMP`, и не теряет последнюю секунду дня.

## Группировка по дням

```sql
SELECT
    date_trunc('day', created_at)::date AS day,
    COUNT(*) AS orders_count,
    SUM(total) AS revenue
FROM orders
WHERE status <> 'cancelled'
GROUP BY day
ORDER BY day;
```

`date_trunc` обрезает время, `::date` убирает лишнюю полночь из вывода.

## Грабли

* **`TIMESTAMP` вместо `TIMESTAMPTZ`.** Если сервер и клиент в разных поясах, «10:30» превратится в разные моменты. Для событий — `TIMESTAMPTZ`.
* **`BETWEEN` по датам.** `BETWEEN '2026-05-01' AND '2026-05-31'` не включает 31 мая после 00:00. Используй `>=` и `<`.
* **`now()` внутри транзакции не меняется.** Это время начала транзакции, а не текущее. Для реального времени — `clock_timestamp()`.
* **Часовой пояс сессии.** `created_at::date` зависит от `TimeZone` сессии. Для отчётов фиксируй пояс явно: `created_at AT TIME ZONE 'Europe/Moscow'`.
* **Дата в текстовом столбце.** `'13.05.2026'` не сравнится с `DATE` так, как ожидается. Храни дату в `DATE` или `TIMESTAMPTZ`.
