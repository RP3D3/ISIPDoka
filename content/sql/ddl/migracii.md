# Миграции

Как менять схему на проекте, где уже есть данные и несколько разработчиков, и не потерять продакшен?

Миграция — это версионированное изменение схемы. Вместо того чтобы вручную выполнять `ALTER TABLE` на каждом окружении, ты хранишь SQL-файлы в репозитории. Инструмент миграций применяет их по порядку и записывает, какие уже выполнены. Так схема на твоём ноутбуке, тестовом сервере и продакшене остаётся одинаковой.

## Как это работает

Представь журнал изменений. Каждая запись имеет номер и описание: «001 — создать таблицу напитков», «002 — добавить описание». Новый разработчик клонирует репозиторий, запускает миграции и получает ту же схему, что у всех. На продакшене применяются только те миграции, которых там ещё нет.

## Пример файла

```sql
-- migrations/001_create_drinks.sql
BEGIN;

CREATE TABLE drinks (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    category TEXT NOT NULL,
    price NUMERIC(10, 2) NOT NULL CHECK (price >= 0),
    is_active BOOLEAN NOT NULL DEFAULT true
);

COMMIT;
```

Следующая миграция:

```sql
-- migrations/002_add_drink_description.sql
ALTER TABLE drinks ADD COLUMN description TEXT;
```

Файлы нумеруются или получают timestamp. Инструмент хранит таблицу вроде `schema_migrations` с уже применёнными версиями.

## Инструменты

| Инструмент | Где встречается |
| --- | --- |
| Flyway | Java, но работает с любой СУБД через SQL |
| Liquibase | XML/YAML/SQL, кроссплатформенный |
| Prisma Migrate | Node.js и TypeScript |
| Django migrations | Python/Django |
| Rails migrations | Ruby on Rails |

Смысл у всех один: версионированные файлы и учёт применённых изменений.

## Правила

- **Одна миграция — одно изменение.** Легче откатить и понять.
- **Не редактируй применённую миграцию.** На продакшене она уже выполнена; изменения разойдутся.
- **Проверяй на копии.** Особенно `ALTER TABLE` на больших таблицах.
- **Планируй откат.** Не все изменения обратимы: `DROP COLUMN` теряет данные.
- **Данные и схема — разные миграции.** Так проще контролировать объём и блокировки.
- **Фиксируй миграции в репозитории.** Схема должна быть воспроизводима с нуля.

## Грабли

* **Ручные правки на продакшене.** Если кто-то выполнил `ALTER TABLE` руками, следующая миграция может упасть или создать дубль.
* **Долгие блокировки.** `ALTER TABLE` на миллионах строк может остановить запись. Используй безопасные паттерны и окна обслуживания.
* **Разрушительные изменения.** `DROP COLUMN`, `TRUNCATE`, смена типа без `USING` — проверь дважды.
* **Миграция данных внутри DDL.** Большой `UPDATE` в той же транзакции увеличит время блокировки. Разделяй.
* **Отсутствие резервной копии.** Перед рискованной миграцией сделай бэкап, даже если есть откат.
* **Разные версии на окружениях.** Проверяй, что тест и продакшен применяют один и тот же набор файлов.
