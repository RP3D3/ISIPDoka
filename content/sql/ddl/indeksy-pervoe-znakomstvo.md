# Индексы: первое знакомство

Почему запрос по `customer_id` находит строку за миллисекунду, а без индекса читает всю таблицу?

Индекс — это дополнительная структура, которая ускоряет поиск. Как алфавитный указатель в книге: вместо чтения всех страниц ты сразу открываешь нужную букву. В PostgreSQL по умолчанию используется B-tree — сбалансированное дерево, которое хорошо работает с равенством, диапазонами и сортировкой.

## Как это работает

Представь картотеку. Без неё ты перебираешь все карточки, чтобы найти клиента. С картотекой — сразу берёшь нужный ящик. Индекс хранит значения столбца в отсортированном виде и ссылки на строки таблицы. База может быстро найти нужное значение, но за это платит местом на диске и замедлением вставок.

## Синтаксис

```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);

CREATE UNIQUE INDEX idx_customers_email ON customers (email);

CREATE INDEX idx_drinks_category_price ON drinks (category, price);

CREATE INDEX idx_active_drinks_price ON drinks (price)
WHERE is_active;

CREATE INDEX idx_drinks_lower_name ON drinks (lower(name));
```

| Индекс | Когда полезен |
| --- | --- |
| обычный | `WHERE`, `JOIN`, `ORDER BY` по столбцу |
| уникальный | дополнительно запрещает повторы |
| составной | условия сразу по нескольким столбцам |
| частичный | поиск только по части строк |
| по выражению | `lower(name)`, `date_trunc(...)` |

## Пример

Запрос ищет заказы клиента:

```sql
SELECT id, created_at, total
FROM orders
WHERE customer_id = 3
ORDER BY created_at DESC;
```

Без индекса база прочитает все заказы. С индексом:

```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);
```

она найдёт нужные строки по дереву. Проверить план можно через `EXPLAIN`:

```sql
EXPLAIN SELECT * FROM orders WHERE customer_id = 3;
```

Если в плане появился `Index Scan` вместо `Seq Scan`, индекс используется.

## Составной индекс

```sql
CREATE INDEX idx_drinks_category_price ON drinks (category, price);
```

Он поможет запросу `WHERE category = 'кофе' AND price < 300`, а также `WHERE category = 'кофе'`. Но не поможет `WHERE price < 300` без категории: в составном индексе порядок столбцов важен, и первый столбец должен участвовать в условии.

## Когда индекс не нужен

- Маленькая таблица: проще прочитать её целиком.
- Столбец с малым числом уникальных значений: например, `is_active` с двумя значениями.
- Таблица, где больше вставок и обновлений, чем чтений: индексы замедляют запись.
- Запрос с ведущим `%` в `LIKE '%латте%'`: обычный B-tree не поможет.

## Грабли

* **Внешний ключ не индексируется автоматически.** PostgreSQL не создаёт индекс по `customer_id` сам. Добавь его вручную.
* **Слишком много индексов.** Каждый индекс занимает место и замедляет `INSERT`, `UPDATE`, `DELETE`.
* **Функция в условии.** `WHERE lower(name) = 'латте'` не использует индекс по `name`. Нужен индекс по `lower(name)`.
* **Составной индекс не универсален.** Порядок столбцов определяет, какие запросы он ускорит.
* **Индекс не гарантирует скорость.** Если строк слишком много или данных мало, планировщик может выбрать `Seq Scan` осознанно.
