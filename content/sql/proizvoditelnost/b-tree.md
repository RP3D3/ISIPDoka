# B-tree

Почему индекс хорошо работает и для `WHERE id = 5`, и для `WHERE price BETWEEN 100 AND 300`, и для `ORDER BY price`?

`B-tree` — сбалансированное дерево, стандартный тип индекса в PostgreSQL. Оно хранит значения в отсортированном порядке и позволяет быстро находить точное значение, диапазон и первые строки сортировки. Понимание B-tree объясняет, почему одни условия используют индекс, а другие нет.

## Как это работает

Представь алфавитный указатель в книге. Чтобы найти слово на «К», ты открываешь середину, понимаешь, что «К» раньше, и сужаешь поиск. B-tree делает то же самое: на каждом уровне отсекает половину оставшихся значений. Глубина дерева растёт логарифмически, поэтому даже миллионы строк находятся за несколько шагов.

## Что умеет B-tree

| Операция | Пример |
| --- | --- |
| равенство | `WHERE id = 5` |
| диапазон | `WHERE price BETWEEN 100 AND 300` |
| сравнение | `WHERE created_at > now() - interval '7 days'` |
| сортировка | `ORDER BY price` |
| префикс `LIKE` | `WHERE name LIKE 'Лат%'` |

## Пример

```sql
CREATE INDEX idx_drinks_price ON drinks (price);

EXPLAIN SELECT name, price
FROM drinks
WHERE price BETWEEN 200 AND 300;
```

```text
Index Scan using idx_drinks_price on drinks
  Index Cond: ((price >= 200) AND (price <= 300))
```

База находит начало диапазона и читает подряд, пока значения не выйдут за границу.

## Что B-tree не умеет

- `WHERE lower(name) = 'латте'` без индекса по выражению.
- `WHERE name LIKE '%латте%'` — ведущий `%` ломает порядок.
- Поиск по массиву или JSON без специального индекса.
- Полнотекстовый поиск — для него есть `GIN`.

## Сортировка

Индекс по `price` может убрать дорогую сортировку:

```sql
EXPLAIN SELECT name, price
FROM drinks
ORDER BY price
LIMIT 10;
```

Если база идёт по индексу, строки уже отсортированы. Для `ORDER BY price DESC` тоже подходит: дерево читается в обратном порядке.

## Грабли

* **`DESC` и `NULLS`.** Для нестандартного порядка может понадобиться индекс с теми же настройками: `CREATE INDEX ... (price DESC NULLS LAST)`.
* **Функция от столбца.** `WHERE lower(name) = ...` не использует индекс по `name`.
* **Ведущий `%`.** `LIKE '%латте%'` не может идти по B-tree.
* **Слишком широкий диапазон.** Если условие выбирает почти всю таблицу, `Seq Scan` дешевле.
* **Много индексов.** Каждый B-tree замедляет вставку и обновление.
* **Низкая селективность.** Индекс по `is_active` с двумя значениями редко полезен.
