# Реляционная модель: таблицы, строки и столбцы

Как организовать хранение взаимосвязанных данных так, чтобы избежать дублирования, противоречий и потери целостности при росте проекта?

Реляционная модель (от англ. *relation* — отношение) представляет всю базу данных в виде набора двумерных таблиц, связанных между собой по общим значениям. В основе подхода лежит математическая теория множеств и реляционная алгебра Эдгара Кодда: каждая строка (`кортеж`) описывает один конкретный экземпляр сущности, а каждый столбец (`атрибут`) задаёт строго типизированное свойство из определённого `домена` значений. В отличие от таблиц Excel или неструктурированных JSON-файлов, реляционная СУБД (`PostgreSQL`) жёстко контролирует структуру схемы, атомарность ячеек и типы данных. Такой подход применяется в большинстве транзакционных систем — от интернет-магазинов до банковских сервисов, где критична точность и согласованность информации.

### Базовые термины и элементы реляционной таблицы

| Инструмент / конструкция | Синтаксис / пример | Назначение и особенности |
| --- | --- | --- |
| **Отношение (`CREATE TABLE`)** | `CREATE TABLE products (...);` | Двумерная таблица, описывающая одну бизнес-сущность (например, товары или пользователей магазина). |
| **Кортеж (Строка / Record)** | `('Ноутбук', 89990.00, true)` | Одна полная запись об объекте в таблице; порядок строк внутри отношения не фиксирован и не несёт смысла. |
| **Атрибут (Столбец / Column)** | `price NUMERIC(10, 2)` | Именованное свойство сущности с единым типом данных для всех записей таблицы. |
| **Домен (Domain)** | `CHECK (price >= 0)` | Множество всех допустимых значений для конкретного атрибута, задаваемое типом данных и ограничениями. |
| **Атомарность ячейки** | `email TEXT` (один адрес) | На пересечении строки и столбца хранится только одно неделимое значение, а не список элементов через запятую. |
| **Схема отношения (Schema)** | `products(id, title, price)` | Формальное описание имени таблицы, списка её столбцов, их типов и правил валидации. |

### Пример кода

```sql
-- 1. Базовый сценарий: создание отношения (таблицы) товаров со строгими доменами атрибутов
CREATE TABLE products (
    id INT GENERATED ALWAYS AS IDENTITY,
    title VARCHAR(150) NOT NULL,
    price NUMERIC(10, 2) NOT NULL CHECK (price >= 0),
    in_stock BOOLEAN NOT NULL DEFAULT true
);

-- 2. Продвинутый сценарий: добавление кортежей (строк) с атомарными значениями
INSERT INTO products (title, price, in_stock)
VALUES
    ('Механическая клавиатура', 7500.00, true),
    ('Беспроводная мышь', 3200.00, true),
    ('Монитор 27" IPS', 28900.00, false);

-- 3. Пограничный случай: выборка без ORDER BY показывает, что таблица — неупорядоченное множество
SELECT title, price
FROM products
WHERE in_stock = true;

-- ❌ Ошибка 1: хранение нескольких значений в одной ячейке через запятую (нарушение атомарности)
-- INSERT INTO products (title, price) VALUES ('Клавиатура, Мышь, Коврик', 11000.00);
-- Почему плохо: невозможно корректно фильтровать, сортировать и обновлять отдельные товары без разбора строк.

-- ❌ Антипаттерн 2: опора на физический порядок вставки строк вместо явной сортировки
-- SELECT * FROM products LIMIT 1; -- в надежде всегда получать самый первый добавленный товар
-- Как правильно: реляционная таблица не гарантирует порядок хранения; всегда используй ORDER BY по ключу или дате.

```

### Важные нюансы

* **Реляционная таблица против листа Excel:** В Excel можно объединить ячейки, записать в один столбец и числа, и текст, или полагаться на визуальный порядок строк сверху вниз. В реляционной БД таблица подчиняется строгим правилам: у строк нет встроенного «номера по порядку», все значения в одном столбце принадлежат одному типу, а каждая ячейка обязана быть атомарной.
* **Ловушка порядка строк без `ORDER BY`:** На маленькой таблице из 5 записей `SELECT * FROM products` обычно возвращает строки в порядке их вставки, создавая иллюзию фиксированной очереди. После первых операций `UPDATE` или `DELETE` PostgreSQL переиспользует освободившиеся страницы памяти (механизм MVCC), и порядок выдачи без явного `ORDER BY` внезапно меняется.
* **Проектирование от сущностей, а не от экранов интерфейса:** В продакшене структуру таблиц строят вокруг реальных бизнес-сущностей предметной области (`users`, `orders`, `products`), а не под внешний вид конкретной формы на сайте. Один экран приложения обычно собирает данные сразу из нескольких связанных таблиц.
* **Связь с теорией и следующей темой:** В примере выше таблица `products` пока не защищена от вставки двух абсолютно одинаковых строк, а сами таблицы существуют изолированно. В следующей карточке (**№ 20 — Первичные и внешние ключи**) разберём, как уникально идентифицировать каждую строку через `PRIMARY KEY` и связать таблицы между собой через `FOREIGN KEY`.
