# Типы связей между таблицами: 1:1, 1:N и M:N

Как правильно определить кардинальность отношений между сущностями и выбрать таблицу для размещения внешнего ключа без дублирования данных?

Кардинальность связи определяет, сколько записей одной таблицы может соответствовать записям другой таблицы, и напрямую диктует расположение `FOREIGN KEY` в схеме базы данных. В реляционном проектировании выделяют три базовых типа отношений: «один к одному» (`1:1`), «один ко многим» (`1:N`) и «многие ко многим» (`M:N`). Если связь `1:N` реализуется добавлением внешнего ключа на сторону «многих», а `1:1` требует дополнительного ограничения `UNIQUE` на `FOREIGN KEY`, то отношение `M:N` в `PostgreSQL` невозможно выразить напрямую без промежуточной таблицы-связки (`junction table`). Грамотный выбор типа связи предотвращает появление повторяющихся столбцов, упрощает запросы и сохраняет консистентность данных при масштабировании схемы.

### Реализация типов связей в PostgreSQL

| Инструмент / конструкция | Синтаксис / пример | Назначение и особенности |
| --- | --- | --- |
| **Один ко многим (`1:N`)** | `user_id INT NOT NULL REFERENCES users(id)` | Самый частый тип связи; внешний ключ всегда размещается в дочерней таблице (на стороне «многих»). |
| **Один к одному (`1:1`)** | `user_id INT PRIMARY KEY REFERENCES users(id)` | Реализуется через `FOREIGN KEY` с ограничением `UNIQUE` (или совмещением с `PK`); используется для выноса редких или чувствительных данных. |
| **Многие ко многим (`M:N`)** | `CREATE TABLE order_items (order_id ..., product_id ...)` | Разбивается на две связи `1:N` через промежуточную таблицу-связку с составным первичным ключом. |
| **Атрибуты связи (Payload)** | `quantity INT NOT NULL, unit_price NUMERIC(10, 2)` | Дополнительные столбцы в промежуточной таблице `M:N`, описывающие характеристики самого факта связи (например, цену товара на момент покупки). |
| **Самоссылающаяся связь (`Self-Join`)** | `parent_id INT REFERENCES categories(id)` | Связь таблицы самой с собой (`1:N`) для хранения древовидных иерархий, например вложенных категорий каталога. |

### Пример кода

```sql
-- 1. Базовый сценарий: связь 1:N (один пользователь оформляет много заказов)
CREATE TABLE users (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE
);

CREATE TABLE orders (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id INT NOT NULL REFERENCES users(id), -- внешний ключ на стороне «многих»
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 2. Продвинутый сценарий: связь M:N с атрибутами (заказы и товары через таблицу order_items)
CREATE TABLE products (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title VARCHAR(150) NOT NULL,
    current_price NUMERIC(10, 2) NOT NULL CHECK (current_price >= 0)
);

CREATE TABLE order_items (
    order_id INT NOT NULL REFERENCES orders(id),
    product_id INT NOT NULL REFERENCES products(id),
    quantity INT NOT NULL CHECK (quantity > 0),
    price_at_purchase NUMERIC(10, 2) NOT NULL CHECK (price_at_purchase >= 0),
    PRIMARY KEY (order_id, product_id)
);

-- 3. Пограничный случай: связь 1:1 для выноса конфиденциальных или редких данных
CREATE TABLE user_profiles (
    user_id INT PRIMARY KEY REFERENCES users(id), -- PK одновременно является FK, что гарантирует 1:1
    full_name VARCHAR(150) NOT NULL,
    phone VARCHAR(20) UNIQUE,
    birth_date DATE
);

-- ❌ Ошибка 1: размещение внешнего ключа на стороне «один» при связи 1:N
-- CREATE TABLE users (id INT PRIMARY KEY, order_id INT REFERENCES orders(id));
-- Почему плохо: один пользователь сможет ссылаться только на один заказ, а попытка записать несколько ID в одну ячейку нарушит атомарность.

-- ❌ Антипаттерн 2: моделирование связи M:N через массивы или пронумерованные столбцы
-- CREATE TABLE orders (id INT PRIMARY KEY, product_ids INT[]);
-- Как правильно: PostgreSQL не поддерживает FOREIGN KEY для элементов массива (можно записать несуществующий ID товара), а также теряется место для хранения количества штук каждого товара; всегда используй таблицу-связку.

```

### Важные нюансы

* **Как безошибочно определить таблицу для `FOREIGN KEY`:** Задайте два встречных вопроса: «Может ли один пользователь иметь много заказов?» (да) и «Может ли один заказ принадлежать нескольким пользователям?» (нет). Внешний ключ всегда ставится в ту таблицу, на вопрос о которой ответ «нет» — то есть в таблицу `orders`, поскольку у заказа ровно один владелец.
* **Ловушка избыточного дробления на `1:1`:** Новички часто разбивают одну сущность на несколько таблиц `1:1` без веской причины, что заставляет СУБД постоянно выполнять лишние операции `JOIN`. Выносить поля в отдельную таблицу `1:1` оправдано только в трёх случаях: для изоляции чувствительных данных с отдельными правами доступа, выноса тяжёлых полей (например, больших текстов или `JSONB`), которые редко нужны в общих списках, либо для опциональных ролей.
* **Фиксация исторического состояния в таблицах `M:N`:** В продакшене промежуточная таблица редко состоит только из двух внешних ключей. В примере выше столбец `price_at_purchase` фиксирует цену товара на момент оформления заказа — без него любое обновление `current_price` в каталоге `products` задним числом исказило бы суммы всех старых закрытых заказов.
* **Связь с теорией и следующей темой:** Правильная расстановка связей `1:N` и развязка `M:N` опираются на первичные и внешние ключи из предыдущей карточки и устраняют дублирование списков в ячейках.
