# Первичные и внешние ключи (PK и FK): уникальность и связи таблиц

Как однозначно идентифицировать каждую строку в таблице и гарантировать, что ссылки между связанными таблицами никогда не укажут на несуществующие данные?

Первичный ключ (`PRIMARY KEY`) однозначно определяет каждый кортеж в таблице, запрещая дубликаты и пустые значения (`NULL`), а внешний ключ (`FOREIGN KEY`) связывает записи двух таблиц, обеспечивая их ссылочную целостность на уровне СУБД. В `PostgreSQL` для генерации суррогатных ключей используют стандартный механизм `GENERATED ALWAYS AS IDENTITY` или глобально уникальные идентификаторы `UUID`, тогда как естественные ключи опираются на реальные бизнес-атрибуты вроде артикула или кода страны. При попытке вставить запись с несуществующим `FOREIGN KEY` или удалить родительскую строку, на которую ссылаются дочерние записи, база данных автоматически заблокирует операцию. Такой механизм применяется во всех реляционных схемах для защиты от «осиротевших» записей и рассинхронизации данных.

### Ключевые конструкции и типы ключей в PostgreSQL

| Инструмент / конструкция | Синтаксис / пример | Назначение и особенности |
| --- | --- | --- |
| **`PRIMARY KEY`** | `id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` | Уникальный идентификатор строки; автоматически создаёт уникальный индекс и запрещает `NULL`. |
| **`GENERATED ALWAYS AS IDENTITY`** | `id BIGINT GENERATED ALWAYS AS IDENTITY` | Современный стандарт автоинкремента в SQL; защищает счётчик от ручной вставки произвольных ID. |
| **`UUID`** | `id UUID DEFAULT gen_random_uuid() PRIMARY KEY` | 128-битный глобально уникальный идентификатор; не раскрывает количество записей и удобен для распределённых систем. |
| **`FOREIGN KEY` (`REFERENCES`)** | `category_id INT REFERENCES categories(id)` | Внешний ключ, гарантирующий, что значение существует в `PRIMARY KEY` (или `UNIQUE`) родительской таблицы. |
| **Составной ключ (Composite Key)** | `PRIMARY KEY (order_id, product_id)` | Первичный ключ из нескольких столбцов; обеспечивает уникальность их комбинации (типично для таблиц-связок). |
| **Естественный ключ (Natural Key)** | `sku VARCHAR(32) PRIMARY KEY` | Ключ на основе существующего бизнес-атрибута (артикул, код валюты); не требует лишнего столбца, но чувствителен к смене правил. |

### Пример кода

```sql
-- 1. Базовый сценарий: первичный ключ (PK) в родительской таблице и внешний ключ (FK) в дочерней
CREATE TABLE categories (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE products (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    category_id INT NOT NULL REFERENCES categories(id),
    title VARCHAR(150) NOT NULL,
    price NUMERIC(10, 2) NOT NULL CHECK (price >= 0)
);

-- 2. Продвинутый сценарий: UUID для публичных сущностей и составной PK для таблицы-связки
CREATE TABLE orders (
    id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
    order_id UUID NOT NULL REFERENCES orders(id),
    product_id INT NOT NULL REFERENCES products(id),
    quantity INT NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, product_id) -- один товар нельзя добавить в один заказ двумя разными строками
);

-- 3. Проверка ссылочной целостности: сначала родительская запись, затем дочерняя
INSERT INTO categories (name) VALUES ('Периферия');
INSERT INTO products (category_id, title, price) VALUES (1, 'Механическая клавиатура', 7500.00);

-- Попытка вставить товар с несуществующим category_id = 999 вызовет ошибку:
-- ERROR: insert or update on table "products" violates foreign key constraint "products_category_id_fkey"

-- ❌ Ошибка 1: использование изменяемого бизнес-поля (например, email) в качестве PRIMARY KEY
-- CREATE TABLE users (email TEXT PRIMARY KEY, full_name TEXT);
-- Почему плохо: при смене почты пользователем придётся обновлять её во всех связанных таблицах заказов и логов.

-- ❌ Антипаттерн 2: использование устаревшего SERIAL вместо GENERATED ALWAYS AS IDENTITY
-- CREATE TABLE brands (id SERIAL PRIMARY KEY, name TEXT);
-- Как правильно: SERIAL позволяет вставить ID вручную без обновления счётчика (sequence), что позже сломает автоинкремент ошибкой duplicate key; используй GENERATED ALWAYS AS IDENTITY.

```

### Важные нюансы

* **Суррогатный ключ против естественного (Surrogate vs Natural):** Естественные ключи (`email`, номер паспорта, артикул) кажутся привлекательными, так как не требуют дополнительного столбца `id`, но при изменении бизнес-правил или формата номера приходится перестраивать связи по всей базе. Суррогатный числовой `INT` / `BIGINT` или `UUID` неизменен на протяжении всей жизни записи, компактно хранится во внешних ключах и ускоряет соединение таблиц.
* **Ловушка отсутствия индекса на `FOREIGN KEY`:** В `PostgreSQL` объявление `PRIMARY KEY` автоматически создаёт индекс, а объявление `FOREIGN KEY` — **нет**. Если у таблицы `products` не создан индекс по столбцу `category_id`, то при каждом удалении или обновлении записи в родительской таблице `categories` СУБД будет выполнять полное сканирование (`Seq Scan`) всей таблицы товаров для проверки ссылочной целостности.
* **Современный стандарт автоинкремента (`IDENTITY` вместо `SERIAL`):** В актуальных версиях PostgreSQL тип `SERIAL` считается устаревшим синтаксическим сахаром, который создаёт скрытую последовательность (`SEQUENCE`) со сложной настройкой прав доступа. В продакшене используют стандартный синтаксис `INT GENERATED ALWAYS AS IDENTITY` (или `BIGINT` для быстрорастущих таблиц), который блокирует случайную ручную подмену идентификаторов.
* **Связь с теорией и следующей темой:** Первичный ключ формально закрывает требование уникальности кортежей из предыдущей карточки, а внешний ключ превращает изолированные таблицы в единую модель данных. В следующей карточке (**№ 30 — Типы связей между таблицами: `1:1`, `1:N` и `M:N**`) разберём, в какой именно таблице размещать `FOREIGN KEY` при разных типах отношений и как правильно проектировать промежуточные таблицы.
