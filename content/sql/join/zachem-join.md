# Зачем JOIN

Почему имя клиента не хранится в каждом заказе и как потом собрать заказ вместе с клиентом?

Если записать имя клиента прямо в заказ, оно продублируется в каждом его заказе. Клиент сменит имя — придётся обновлять десятки строк и надеяться, что ни одну не пропустили. Поэтому в базе хранят только `customer_id`, а имя живёт в одном месте — в таблице `customers`. `JOIN` собирает данные обратно по этому ключу.

## Как это работает

Представь два списка: в одном — заказы с номером клиента, в другом — клиенты с их номерами. `JOIN` берёт заказ, смотрит на `customer_id`, находит в справочнике клиента с таким же `id` и приклеивает его имя к заказу. Если пары нет, строка либо пропадает, либо остаётся с пустым местом — зависит от типа соединения.

## Синтаксис

```sql
SELECT столбцы
FROM таблица_1 AS a
JOIN таблица_2 AS b ON b.ключ = a.внешний_ключ;
```

`ON` — условие сопоставления. Обычно это равенство внешнего ключа и первичного ключа, но могут быть и более сложные условия.

| Тип | Что оставляет |
| --- | --- |
| `INNER JOIN` | только пары, найденные с обеих сторон |
| `LEFT JOIN` | все строки левой таблицы, даже без пары |
| `RIGHT JOIN` | все строки правой таблицы, даже без пары |
| `FULL JOIN` | все строки с обеих сторон |
| `CROSS JOIN` | все возможные комбинации |

## Пример

Заказы с именами клиентов:

```sql
SELECT
    o.id AS order_id,
    c.name AS customer,
    o.total
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
ORDER BY o.id DESC
LIMIT 5;
```

| order_id | customer | total |
| --- | --- | --- |
| 128 | Анна | 640.00 |
| 127 | Игорь | 280.00 |
| 126 | Анна | 410.00 |
| 125 | Мария | 320.00 |
| 124 | Павел | 500.00 |

В результате снова «одна большая таблица», но она собрана на лету. В базе по-прежнему два отдельных набора данных.

## Зачем разделять

- **Меньше дублей.** Имя клиента хранится один раз, а не в каждом заказе.
- **Проще обновлять.** Сменил телефон — обновил одну строку.
- **Легче проверять.** Внешний ключ не даст создать заказ для несуществующего клиента.
- **Гибче строить отчёты.** Одни и те же данные можно соединить по-разному: заказы с клиентами, заказы с напитками, напитки с ингредиентами.

## Грабли

* **`JOIN` без `ON`.** Это уже не соединение по ключу, а `CROSS JOIN`: каждая строка с каждой. На больших таблицах результат взрывается.
* **Соединение не по тому ключу.** Если перепутать `customer_id` и `drink_id`, пары найдутся, но бессмысленные.
* **Дубли после соединения.** Если в правой таблице несколько строк на одну левую, результат размножится. Это нормально для `order_items`, но опасно для сумм.
* **`NULL` не находит пару.** Если `customer_id` пустой, `JOIN` по равенству не найдёт клиента.
