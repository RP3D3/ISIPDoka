# Многие ко многим

Как хранить рецепты напитков, если один напиток состоит из многих ингредиентов, а один ингредиент входит во многие напитки?

Связь «многие ко многим» нельзя выразить одним внешним ключом. Если положить `ingredient_id` в `drinks`, у напитка будет только один ингредиент. Если положить `drink_id` в `ingredients`, ингредиент будет только в одном напитке. Поэтому между ними ставят третью таблицу — `drink_ingredients`, где каждая строка означает «в этом напитке столько этого ингредиента».

## Как это работает

Представь рецептурную книгу. На каждой странице — напиток и список ингредиентов. Но один и тот же сироп встречается на многих страницах. Чтобы не переписывать его свойства на каждой странице, заводят два справочника: напитки и ингредиенты, а между ними — карточки связей «напиток + ингредиент + количество».

## Схема связи

```sql
CREATE TABLE drink_ingredients (
    drink_id BIGINT REFERENCES drinks(id),
    ingredient_id BIGINT REFERENCES ingredients(id),
    amount NUMERIC(8, 2) NOT NULL,
    PRIMARY KEY (drink_id, ingredient_id)
);
```

Составной первичный ключ `(drink_id, ingredient_id)` не даёт дважды добавить один ингредиент в один напиток.

## Пример

Рецепт латте:

```sql
SELECT
    d.name AS drink,
    i.name AS ingredient,
    di.amount,
    i.unit
FROM drinks AS d
JOIN drink_ingredients AS di ON di.drink_id = d.id
JOIN ingredients AS i ON i.id = di.ingredient_id
WHERE d.name = 'Латте'
ORDER BY i.name;
```

| drink | ingredient | amount | unit |
| --- | --- | --- | --- |
| Латте | Кофе (зерно) | 18.00 | г |
| Латте | Молоко | 250.00 | мл |

Себестоимость каждого напитка:

```sql
SELECT
    d.name,
    ROUND(SUM(di.amount * i.cost_per_unit), 2) AS cost
FROM drinks AS d
JOIN drink_ingredients AS di ON di.drink_id = d.id
JOIN ingredients AS i ON i.id = di.ingredient_id
GROUP BY d.name
ORDER BY cost DESC;
```

| name | cost |
| --- | --- |
| Какао | 61.50 |
| Латте | 41.60 |
| Матча-латте | 40.00 |
| Капучино | 33.60 |
| Американо | 23.60 |
| Эспрессо | 21.90 |
| Чай с бергамотом | 15.00 |
| Лимонад | 12.25 |

`SUM(di.amount * i.cost_per_unit)` считает стоимость всех ингредиентов напитка. Три таблицы соединяются по цепочке: напиток → связь → ингредиент.

## Почему не список в ячейке

Можно было бы хранить `ingredients = 'кофе, молоко'` в одной ячейке. Но тогда:

- нельзя посчитать количество и себестоимость;
- нельзя быстро найти все напитки с молоком;
- нельзя проверить, что ингредиент существует;
- придётся парсить строку в каждом запросе.

Третья таблица решает всё это обычными `JOIN` и агрегатами.

## Грабли

* **Забыть `amount`.** Связь без количества бессмысленна для рецепта и себестоимости.
* **Дубли в промежуточной таблице.** Составной первичный ключ должен запрещать повтор пары.
* **Соединять только две таблицы из трёх.** Без `ingredients` не получить название и цену ингредиента.
* **Суммировать без `GROUP BY`.** Иначе получится одна общая себестоимость всех напитков.
* **Путать `drink_ingredients` с заказом.** Это рецепт, а не факт продажи. Продажи лежат в `order_items`.
