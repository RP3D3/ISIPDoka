# Ошибки JOIN и дубли

Почему после `JOIN` выручка выросла в полтора раза, хотя данные не менялись?

Соединение с таблицей, где на одну левую строку приходится несколько правых, размножает результат. Для списка позиций это нормально, но для суммы заказов — катастрофа: один и тот же `total` складывается столько раз, сколько у заказа позиций. Это называется fan-out. Лечится не `DISTINCT`, а правильным выбором таблицы для агрегата.

## Как это работает

Представь, что у заказа 128 две позиции. После `JOIN` с `order_items` заказ 128 превращается в две строки, и в каждой стоит `total = 640`. Если сложить `total` по всем таким строкам, 640 посчитается дважды. Данные не изменились — изменился уровень детализации.

## Пример

Сначала правильная сумма:

```sql
SELECT SUM(total) AS revenue
FROM orders;
```

| revenue |
| --- |
| 3600.00 |

Теперь сумма после соединения с позициями:

```sql
SELECT SUM(o.total) AS wrong_revenue
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id;
```

| wrong_revenue |
| --- |
| 5910.00 |

Разница — 2310.00. Это не ошибка базы: каждая позиция добавила копию заказа.

Правильный вариант — суммировать позиции или агрегировать заказы до соединения:

```sql
SELECT SUM(oi.quantity * oi.unit_price) AS revenue
FROM order_items AS oi
JOIN orders AS o ON o.id = oi.order_id
WHERE o.status IN ('paid', 'done');
```

| revenue |
| --- |
| 3040.00 |

## Как заметить fan-out

```sql
SELECT
    COUNT(*) AS rows_after_join,
    COUNT(DISTINCT o.id) AS distinct_orders
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id;
```

| rows_after_join | distinct_orders |
| --- | --- |
| 13 | 9 |

Тринадцать строк на девять заказов — признак того, что соединение размножило заказы. Если `COUNT(*)` больше `COUNT(DISTINCT id)`, проверь, не суммируешь ли ты левую таблицу после соединения.

## Частые ошибки

| Ошибка | Что происходит |
| --- | --- |
| Забыли `ON` | `CROSS JOIN`, строки размножаются |
| Соединили по неключевому полю | ложные пары и дубли |
| Суммируют левую таблицу после `JOIN` | сумма завышена |
| `LEFT JOIN` + фильтр правой таблицы в `WHERE` | соединение превращается в `INNER` |
| `NULL` в ключе | пара не находится |
| `DISTINCT` вместо исправления | дубли скрыты, но сумма может остаться неверной |

## Грабли

* **`DISTINCT` не лечит fan-out.** `SUM(DISTINCT o.total)` сработает только если суммы уникальны. В реальных данных это не так.
* **Сначала агрегируй, потом соединяй.** Если нужна сумма заказов, не соединяй их с позициями до агрегата.
* **Проверяй гранулярность.** Спроси себя: «Что означает одна строка результата?» Заказ, позиция или пара?
* **`COUNT(*)` после `JOIN`.** Он считает строки результата, а не сущности. Для сущностей — `COUNT(DISTINCT id)`.
* **`NULL` не равен `NULL`.** Соединение по `NULL` не найдёт пару; для таких случаев нужен `IS NOT DISTINCT FROM` или `COALESCE`.
