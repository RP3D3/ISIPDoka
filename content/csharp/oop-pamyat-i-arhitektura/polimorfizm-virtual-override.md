# Полиморфизм virtual, override

Как сложить воина, мага и крестьянина в один общий список `List<Character>` и заставить каждого атаковать по-своему одной командой `unit.Attack()`, без громоздких проверок `if (unit is Mage)`?

:::gap

## Кратко

Полиморфизм позволяет работать с разными классами-наследниками через единый базовый тип, при этом каждый объект выполняет собственную версию действия. Ключевое слово `virtual` в родительском классе разрешает наследникам менять поведение метода или свойства, а `override` в дочернем классе задаёт новую реализацию. Это избавляет код от десятков проверок типов и позволяет легко добавлять новых персонажей в игру, не переписывая основной боевой цикл.

:::gap

## Быстрый пример

Соберём отряд из разных классов-наследников в один список базового типа и вызовем у каждого метод `Attack()`:

```cs
// Храним разных наследников в одном общем списке базового типа
List<Character> party = [new Warrior("Артур"), new Mage("Лира"), new Character("Крестьянин")];

foreach (Character unit in party)
{
    unit.Attack(); // Каждый вызовет свою версию метода Attack
}

class Character(string name)
{
    public string Name { get; } = name;

    // virtual разрешает наследникам переопределить метод
    public virtual void Attack()
    {
        Console.WriteLine($"{Name} бьёт кулаком (5 урона)");
    }
}

class Warrior(string name) : Character(name)
{
    // override заменяет поведение базового метода
    public override void Attack()
    {
        Console.WriteLine($"{Name} рубит двуручным мечом (25 урона)");
    }
}

class Mage(string name) : Character(name)
{
    public override void Attack()
    {
        Console.WriteLine($"{Name} запускает огненный шар (35 урона)");
    }
}

```

:::gap

## Как это работает

При выполнении кода среда .NET связывает вызов метода не с типом переменной, а с реальным классом созданного объекта:

1. **Единая коллекция (`List<Character>`).** Поскольку `Warrior` и `Mage` наследуются от `Character`, их можно положить в один общий список родительского типа. Для цикла `foreach` все элементы выглядят просто как `Character`.
2. **Разрешение на изменение (`virtual`).** В базовом классе `Character` метод `Attack` помечен словом `virtual`. Это означает: «у меня есть стандартная атака кулаком, но наследники могут заменить её своей».
3. **Переопределение логики (`override`).** Классы `Warrior` и `Mage` используют модификатор `override`, чтобы подставить собственную реализацию атаки. Крестьянин же `override` не писал, поэтому использует родительский вариант.
4. **Динамическая диспетчеризация (`unit.Attack()`).** Хотя переменная `unit` объявлена с типом `Character`, во время работы программы среда .NET смотрит на реальный объект в памяти и запускает нужный метод: меч для воина, заклинание для мага и кулак для крестьянина.

> [!TIP]
> Модификаторы `virtual` и `override` работают не только для методов, но и для свойств и индексаторов — например, можно сделать виртуальным свойство `public virtual int Speed => 10;` и переопределить его в наследнике.

:::gap

## Грабли и частые ошибки

### 1. Попытка переопределить метод без `virtual` в родителе

* **Так не скомпилируется:** написать `public override void Attack()` в наследнике, если в базовом классе метод объявлен просто как `public void Attack()`. По умолчанию все методы в C# невиртуальные, поэтому компилятор выдаст ошибку `CS0506`.
* **Так правильно:** добавить модификатор `virtual` (или `abstract`) в объявление метода в базовом классе.

### 2. Случайное сокрытие метода вместо переопределения (забытый `override`)

* **Так сработает неправильно:** написать в наследнике `public void Attack()` без слова `override` (или с модификатором `new`). Компилятор выдаст предупреждение `CS0108`, а при вызове через базовую ссылку `Character unit = new Warrior("Артур"); unit.Attack();` запустится **старый метод родителя** вместо метода воина.
* **Так правильно:** всегда использовать `override`, чтобы поведение менялось полиморфно независимо от типа переменной.

### 3. Попытка сделать метод `virtual` вместе с `private` или `static`

* **Так не скомпилируется:** написать `private virtual void Calc()` или `public static virtual void Calc()` (ошибки `CS0621` и `CS0112`). Приватные методы не видны наследникам, а статичные привязаны к классу, а не к объекту, поэтому переопределять их бессмысленно.
* **Так правильно:** использовать `virtual` только для обычных (экземплярных) методов с доступом `public`, `protected` или `internal`.

### 4. Вызов виртуального метода внутри конструктора базового класса

* **Так упадёт:** вызвать `Attack()` прямо внутри конструктора `Character`. На момент работы конструктора родителя поля дочернего класса `Mage` ещё не инициализированы, и обращение к ним внутри переопределённого `override Attack()` приведёт к `NullReferenceException` или работе с пустыми значениями.
* **Так правильно:** никогда не вызывать `virtual`-методы из конструкторов — инициализируйте данные в полях, а виртуальные действия запускайте после создания объекта.

:::gap

## Под капотом и нюансы

### Таблица виртуальных методов (`MethodTable` / vtable)

При загрузке каждого класса в память среда CLR строит для него служебную таблицу адресов методов (**MethodTable**). Для каждого `virtual`-метода в этой таблице выделяется фиксированный слот (ячейка):

* В таблице класса `Character` в слоте `Attack` записан адрес метода `Character.Attack`.
* В таблице наследника `Warrior` в **том же самом** слоте перезаписан адрес `Warrior.Attack`.

Когда процессор выполняет `unit.Attack()`, он считывает указатель на `MethodTable` из заголовка объекта в куче, заглядывает в нужный слот и мгновенно переходит по адресу за `O(1)` — без поиска по именам и без проверок `if`.

### Запрет дальнейшего переопределения (`sealed override`)

Если вы переопределили метод в классе `Warrior`, но хотите запретить его дальнейшим наследникам (например, `Berserk : Warrior`) снова менять эту логику, добавьте слово `sealed` перед `override`:

```cs
class Warrior(string name) : Character(name)
{
    public sealed override void Attack() => Console.WriteLine($"{Name} бьёт мечом");
}

```

Это не только защитит логику от изменений, но и поможет JIT-компилятору выполнить девиртуализацию и встроить код метода напрямую для ускорения работы.

### Сравнение переопределения (`override`) и сокрытия (`new`)

| Критерий | Переопределение (`override`) | Сокрытие (`new`) |
| --- | --- | --- |
| Требует `virtual` в родителе | **Да** | Нет (работает для любого метода) |
| Вызов через `Character x = new Warrior()` | Запустит метод **наследника** (`Warrior`) | Запустит метод **родителя** (`Character`) |
| Вызов через `Warrior x = new Warrior()` | Запустит метод **наследника** (`Warrior`) | Запустит метод **наследника** (`Warrior`) |
| Главный сценарий | Настоящий полиморфизм | Редкая замена метода в чужой библиотеке без исходного кода |
