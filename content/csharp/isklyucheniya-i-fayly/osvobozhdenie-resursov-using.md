# Освобождение ресурсов (using)

Как гарантированно закрыть файл, сетевое соединение или подключение к базе данных сразу после работы, даже если внутри метода внезапно произошла ошибка?

:::gap

## Кратко

Сборщик мусора (*Garbage Collector*) в .NET сам очищает оперативную память, но ничего не знает о внешних ресурсах операционной системы: открытых файлах, сетевых сокетах и соединениях с базой данных. Конструкция `using` гарантирует, что у объекта автоматически вызовется метод `Dispose()`, как только программа выйдет из текущего блока кода или метода — даже если внутри произойдёт сбой и выбросится исключение. Это защищает приложение от утечек ресурсов и ошибок вида «файл занят другим процессом».

:::gap

## Быстрый пример

Запишем данные в файл через современное объявление `using` и создадим свой класс с поддержкой автоматической очистки:

```cs
WriteLog("Сервер успешно запущен");

// Собственный класс с поддержкой using
using (var session = new NetworkSession("192.168.1.10"))
{
    session.Send("PING");
} // Здесь автоматически вызовется session.Dispose()

void WriteLog(string message)
{
    // Объявление using: файл автоматически закроется при выходе из метода WriteLog
    using StreamWriter writer = new("app.log", append: true);
    writer.WriteLine($"{DateTime.Now:HH:mm:ss} — {message}");
}

class NetworkSession(string host) : IDisposable
{
    public void Send(string data) => Console.WriteLine($"Отправка [{data}] на {host}");

    public void Dispose()
    {
        Console.WriteLine($"Соединение с {host} закрыто");
    }
}

```

:::gap

## Как это работает

При компиляции и выполнении кода среда .NET связывает область видимости переменной с освобождением занятых ею ресурсов:

1. **Контракт `IDisposable`.** Использовать конструкцию `using` можно только с объектами, которые реализуют стандартный интерфейс `IDisposable` (у них есть метод `void Dispose()`). В стандартной библиотеке этот интерфейс есть у `StreamWriter`, `FileStream`, `HttpClient`, `SqlConnection` и десятков других классов.
2. **Современное объявление (`using StreamWriter writer = ...`).** Если написать `using` перед объявлением локальной переменной без фигурных скобок, ресурс останется открытым до конца текущего блока или метода, а при выходе из него среда автоматически вызовет `writer.Dispose()`.
3. **Классический блок (`using (var session = ...) { ... }`).** Фигурные скобки позволяют задать точные границы жизни ресурса. Как только управление доходит до закрывающей скобки `}`, соединение закрывается, даже если до конца метода ещё сто строк кода.
4. **Защита при исключениях.** Если внутри `WriteLog` произойдёт сбой, файл всё равно будет корректно закрыт и сохранит буфер на диск — `using` сработает при любом сценарии выхода из блока.

> [!TIP]
> Предпочитайте современную запись `using var ...` без лишних фигурных скобок — она избавляет код от «лесенки» вложенности. Классический блок `using (...) { ... }` оставляйте только для случаев, когда файл или блокировку нужно освободить в середине длинного метода.

:::gap

## Грабли и частые ошибки

### 1. Попытка применить `using` к обычному классу без `IDisposable` (`CS1674`)

* **Так не скомпилируется:** написать `using var hero = new Hero();`, если класс `Hero` не реализует интерфейс `IDisposable` (или `IAsyncDisposable`). Компилятор остановит сборку с ошибкой `CS1674`.
* **Так правильно:** использовать `using` только для типов, управляющих внешними ресурсами, либо реализовать интерфейс `IDisposable` в своём классе.

### 2. Возврат ресурса, объявленного через `using`, из метода (`ObjectDisposedException`)

* **Так упадёт:** написать в методе `using FileStream fs = File.OpenRead("data.bin"); return fs;`. При выходе из метода `using` немедленно закроет поток, и вызывающий код получит уже мёртвый закрытый объект, который рухнет с `ObjectDisposedException` при попытке чтения.
* **Так правильно:** если метод создаёт и отдаёт ресурс наружу, не ставить `using` внутри этого метода — пусть `using` напишет тот код, который получит и использует этот поток.

### 3. Использование обычного `using` вместо `await using` для асинхронных ресурсов

* **Так сработает неправильно:** закрывать асинхронные потоки или транзакции базы данных (реализующие `IAsyncDisposable`) обычным синхронным `using` внутри `async`-метода, блокируя поток на время сброса буфера.
* **Так правильно:** в асинхронных методах использовать конструкцию `await using var stream = new FileStream(...);` — она корректно дождётся асинхронного метода `DisposeAsync()`.

### 4. Обращение к объекту после закрытия блока `using`

* **Так упадёт:** сохранить ссылку на поток во внешнюю переменную до блока `using (stream) { ... }`, а после закрывающей скобки попытаться вызвать `stream.Read(...)` — программа выбросит `ObjectDisposedException`.
* **Так правильно:** всегда создавать переменную прямо внутри объявления `using` и выполнять все операции с ресурсом строго до его закрытия.

:::gap

## Под капотом и нюансы

### Во что компилируется `using` (разворачивание в `try / finally`)

На уровне промежуточного языка IL конструкции `using` не существует — это синтаксический сахар компилятора Roslyn. Любой блок `using` компилятор прозрачно превращает в связку `try / finally` с проверкой на `null`:

```cs
// Ваш код:
using (var writer = new StreamWriter("app.log"))
{
    writer.WriteLine("Привет");
}

// Во что его превращает компилятор:
var writer = new StreamWriter("app.log");
try
{
    writer.WriteLine("Привет");
}
finally
{
    if (writer is not null)
    {
        ((IDisposable)writer).Dispose();
    }
}

```

Именно благодаря блоку `finally` метод `Dispose()` гарантированно вызывается даже при досрочном `return` или неперехваченном исключении.

### Сравнение способов освобождения ресурсов

| Синтаксис | Когда вызывается очистка | Когда лучше использовать |
| --- | --- | --- |
| `using var x = ...;` | В конце текущего блока `{ }` или всего метода | В 90% случаев — чистый код без лишних отступов |
| `using (var x = ...) { }` | Сразу на закрывающей скобке `}` этого блока | Когда ресурс нужно освободить до конца длинного метода |
| `await using var x = ...;` | В конце области видимости асинхронно (`DisposeAsync`) | В `async`-методах при работе с файлами, сетью и БД |
| `x.Dispose()` вручную | В момент прямого вызова метода | Когда объект живёт как поле другого `IDisposable`-класса |

### Финализаторы (`~ClassName`) и `ref struct`

* **Деструктор (финализатор) `~MyClass()`.** В C# можно объявить финализатор, который сборщик мусора вызовет перед удалением объекта из памяти. Однако полагаться только на него нельзя: неизвестно, когда именно запустится GC (может пройти минута или час), поэтому файл всё это время останется заблокированным. Финализатор используют лишь как последнюю страховку внутри сложных обёрток над неуправляемыми указателями (`IntPtr`).
* **Утиный `Dispose()` для `ref struct`.** Значимые структуры `ref struct` (например, `Span`-обёртки) не могут реализовывать интерфейсы, поэтому компилятор разрешает использовать с ними `using`, если у структуры просто объявлен публичный метод `public void Dispose()`.
