# Сборщик мусора (GC) и поколения кучи

Как среда .NET автоматически освобождает память без ручного вызова `free()`, почему массивы больше 85 КБ попадают в отдельную кучу и откуда в управляемом коде берутся реальные утечки памяти?

Сборщик мусора (**Garbage Collector**, `GC`) в .NET автоматически управляет памятью в управляемой куче (*Managed Heap*), отслеживая граф достижимых объектов от «корней» (*GC Roots*: локальные переменные в стеке, статические поля, регистры процессора). Чтобы не сканировать всю память программы при каждой очистке, куча разделена на три поколения (**Gen 0**, **Gen 1**, **Gen 2**) по гипотезе «молодые объекты умирают быстро», а крупные объекты от $85\,000$ байт сразу размещаются в отдельной куче больших объектов (**LOH**). Несмотря на работу GC, забытые подписки на события, бесконечно растущие статические кэши и неосвобождённые неуправляемые ресурсы приводят к реальным утечкам памяти.

## Устройство кучи и инструменты диагностики GC

| Понятие / инструмент | Синтаксис / характеристика | Назначение и как работает |
| --- | --- | --- |
| **Поколения Gen 0, Gen 1, Gen 2** | `GC.GetGeneration(obj)` | Короткоживущие, буферные и долгоживущие объекты; чем старше поколение, тем реже оно очищается |
| **Large Object Heap (LOH)** | Объекты $\ge 85\,000$ байт | Отдельная область кучи для крупных массивов и строк; по умолчанию не сжимается ради экономии CPU |
| **`WeakReference<T>`** | `var weak = new WeakReference<byte[]>(data);` | Слабая ссылка: позволяет кэшировать объект, не мешая сборщику мусора удалить его при дефиците ОЗУ |
| **Финализатор (`~ClassName`)** | `GC.SuppressFinalize(this)` | Резервный метод очистки неуправляемых ресурсов перед удалением объекта (продлевает жизнь на 1 сборку) |
| **Диагностика памяти** | `GC.GetTotalMemory(false)` / `GC.CollectionCount(0)` | Показывают текущий объём занятой кучи в байтах и число прошедших сборок по поколению |

## Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        // 1. Обычный небольшой объект попадает в самое молодое поколение — Gen 0
        byte[] smallBuffer = new byte[1024];
        Console.WriteLine($"Поколение малого буфера (1 КБ):   Gen {GC.GetGeneration(smallBuffer)}");

        // 2. Объект размером от 85 000 байт сразу попадает в LOH (логически относится к Gen 2)
        byte[] largeBuffer = new byte[85_000];
        Console.WriteLine($"Поколение большого буфера (85 КБ): Gen {GC.GetGeneration(largeBuffer)} (LOH)");

        // 3. WeakReference<T>: кэшируем тяжёлые данные так, чтобы GC мог забрать их при необходимости
        WeakReference<byte[]> weakCache = CreateWeakCache();

        if (weakCache.TryGetTarget(out byte[]? aliveBeforeGc))
        {
            Console.WriteLine($"\nДо сборки мусора кэш доступен: {aliveBeforeGc.Length} байт");
        }

        // Принудительный вызов GC.Collect() допустим только в тестах и учебных примерах для демонстрации!
        aliveBeforeGc = null;
        GC.Collect();
        GC.WaitForPendingFinalizers();

        bool isStillAlive = weakCache.TryGetTarget(out _);
        Console.WriteLine($"После сборки мусора кэш жив: {isStillAlive}");
        Console.WriteLine($"Занято в управляемой куче: {GC.GetTotalMemory(forceFullCollection: false):N0} байт");

        // ❌ Ошибка 1: вызов GC.Collect() в рабочем коде ломает самонастройку порогов поколений
        // и преждевременно переводит временные объекты в старшие поколения

        // ❌ Ошибка 2 (Утечка памяти через события): если долгоживущий publisher подписан на короткоживущий
        // объект (publisher.Changed += tempObj.OnChanged) и не выполнена отписка (-=), tempObj не удалится
    }

    static WeakReference<byte[]> CreateWeakCache()
    {
        byte[] heavyData = new byte[50_000];
        return new WeakReference<byte[]>(heavyData);
    }
}

```

## Важные нюансы

* **Как работают поколения (Gen 0, Gen 1, Gen 2) и фаза сжатия (*Compaction*):** при заполнении Gen 0 запускается сверхбыстрая сборка (занимает доли миллисекунды): живые объекты копируются в Gen 1 и сдвигаются вплотную друг к другу (*compaction*), полностью устраняя фрагментацию памяти, а мёртвые перезаписываются. Выжившие при следующей проверке Gen 1 переходят в Gen 2 — полная сборка этого поколения (*Full GC*) проходит редко, но приостанавливает потоки программы (*Stop-The-World*) на заметное время.
* **Куча больших объектов (LOH) и закреплённых объектов (POH):** любой объект размером от $85\,000$ байт (например, `new byte[85_000]` или `new int[21_250]`) минует Gen 0 и сразу попадает в LOH, которая собирается только вместе с Gen 2. Копировать мегабайтные массивы при сжатии слишком дорого, поэтому LOH по умолчанию не уплотняется — частые создания крупных массивов ведут к фрагментации памяти (для буферов, закреплённых в памяти через `GCHandle` или `fixed`, в .NET 5+ выделена отдельная *Pinned Object Heap* — POH).
* **Откуда берутся утечки памяти при работающем GC:** сборщик мусора удаляет только те объекты, до которых невозможно добраться по цепочке ссылок от *GC Roots*. Типичные причины утечек в C#: долгоживущий издатель события удерживает ссылку на короткоживущего подписчика (`event += ...` без `-=`), статический `Dictionary` накапливает данные без политики вытеснения или класс с неуправляемым дескриптором ОС не реализует `IDisposable`. Если нужно хранить кэш, который разрешено очистить при нехватке ОЗУ, используйте `WeakReference<T>`.
* **Почему `GC.Collect()` вреден и связь со следующей темой:** вызов `GC.Collect()` вручную сбивает внутреннюю статистику CLR и переводит объекты, которые умерли бы через миллисекунду, в Gen 1 и Gen 2, где их очистка обойдётся в разы дороже. Вместо ручного запуска сборки мусора в высоконагруженном коде стараются вовсе не выделять новые буферы в куче — в следующей карточке мы разберём, как арендовать готовые массивы и работать со стековой памятью (*`Memory<T>`, `ArrayPool<T>` и `stackalloc*`).
