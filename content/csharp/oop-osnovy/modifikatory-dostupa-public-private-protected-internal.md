# Модификаторы доступа (public, private, protected, internal)

Как скрыть секретный PIN-код или внутренний счётчик баланса внутри класса, чтобы остальной код не мог их случайно сломать, но при этом открыть безопасные кнопки управления?

:::gap

## Кратко

Модификаторы доступа определяют правила видимости: какие части программы могут читать или изменять конкретный класс, поле, свойство или метод. В C# есть четыре базовых уровня: `public` (открыто для всех), `private` (только внутри текущего класса), `protected` (внутри класса и его наследников) и `internal` (внутри текущего проекта, но скрыто от внешних библиотек). Это главный инструмент **инкапсуляции** — защиты внутреннего устройства объекта от случайного вмешательства извне.

:::gap

## Быстрый пример

Создадим базовый счёт `BankAccount` и его наследника `BonusAccount`, чтобы увидеть все четыре модификатора в деле:

```cs
BonusAccount account = new();
account.Deposit(1000);           // public: доступно везде
account.ApplyWelcomeBonus();     // public: внутри вызывает protected-метод
account.AuditLog();              // internal: доступно внутри текущего проекта

// account._pinCode = "0000";    // Ошибка: private скрыт от внешнего кода
// account.AddBonus(50);         // Ошибка: protected виден только наследникам

Console.WriteLine($"Баланс: {account.Balance}"); // [AUDIT] Баланс: 1050 -> Баланс: 1050

class BankAccount
{
    private string _pinCode = "1234";      // Только внутри BankAccount
    protected decimal _balance;            // Внутри BankAccount и его наследников

    public decimal Balance => _balance;    // Открыто для всех

    public void Deposit(decimal amount)
    {
        if (amount > 0) _balance += amount;
    }

    protected void AddBonus(decimal bonus) => _balance += bonus;

    internal void AuditLog() => Console.WriteLine($"[AUDIT] Баланс: {_balance}");
}

class BonusAccount : BankAccount
{
    public void ApplyWelcomeBonus()
    {
        AddBonus(50); // Работает: метод AddBonus имеет модификатор protected
        // Console.WriteLine(_pinCode); // Ошибка: private не виден даже наследнику
    }
}

```

:::gap

## Как это работает

При компиляции и запуске кода среда .NET проверяет права доступа к каждому элементу по строгой иерархии границ:

1. **Максимальная изоляция (`private`).** Поле `_pinCode` доступно только между фигурными скобками самого класса `BankAccount`. Ни внешний код в `Program.cs`, ни даже дочерний класс `BonusAccount` не могут его увидеть или изменить.
2. **Семейный доступ для наследников (`protected`).** Поле `_balance` и метод `AddBonus` скрыты от посторонних (`account.AddBonus(50)` снаружи не скомпилируется), но открыты для всех классов, которые наследуются от `BankAccount` (`class BonusAccount : BankAccount`).
3. **Доступ внутри своей сборки (`internal`).** Метод `AuditLog` виден любому классу внутри текущего проекта (`.csproj`), но если вы скомпилируете этот проект в библиотеку `.dll` и подключите к другой программе, метод окажется скрыт.
4. **Открытый интерфейс (`public`).** Свойство `Balance` и метод `Deposit` доступны из любой точки программы и из любых внешних проектов — это официальные «кнопки управления» объектом.

> [!TIP]
> Придерживайтесь принципа минимальных привилегий: по умолчанию делайте все поля, свойства и вспомогательные методы `private`, а `public` ставьте только на те члены, которые действительно нужны внешнему коду.

:::gap

## Грабли и частые ошибки

### 1. Забытый модификатор доступа (неявные значения по умолчанию)

* **Так не скомпилируется:** написать внутри класса `int Hp = 100;` без модификатора и попытаться прочитать `player.Hp` снаружи (ошибка `CS0122` — недоступно из-за уровня защиты). Внутри класса и структуры всё по умолчанию `private`, а сами классы в пространстве имён по умолчанию `internal`.
* **Так правильно:** явно указывать `public` для открытых членов класса, а для `private` также желательно писать слово явно ради читаемости.

### 2. Несогласованная доступность типов (`CS0053`)

* **Так не скомпилируется:** объявить `internal class Weapon { }` и использовать его в публичном свойстве публичного класса: `public class Hero { public Weapon Sword { get; set; } }`. Внешний проект увидит класс `Hero`, но не сможет работать с типом `Weapon`, поэтому сборка остановится с ошибкой `CS0053`.
* **Так правильно:** следить, чтобы тип параметра или возвращаемого значения публичного метода/свойства был не менее открытым (`public`), чем сам метод или свойство.

### 3. Использование `protected` в структуре или `sealed`-классе

* **Так не скомпилируется:** объявить `protected int x;` внутри `struct Point` (ошибка `CS0666`, так как структуры не поддерживают наследование) или получить предупреждение `CS0628` в классе с модификатором `sealed`, от которого запрещено наследоваться.
* **Так правильно:** в структурах и `sealed`-классах использовать `private` или `internal`.

### 4. Путаница между `protected internal` и `private protected`

* **Так сработает неправильно:** написать `protected internal` в надежде разрешить доступ «только наследникам внутри текущей сборки». На самом деле `protected internal` работает как логическое **ИЛИ**: доступ получит либо наследник из любого проекта, либо вообще любой класс из текущей сборки.
* **Так правильно:** для строгого условия **И** («только наследник И только внутри текущей сборки») использовать связку `private protected`.

:::gap

## Под капотом и нюансы

### Полная таблица уровней доступа в C#

Помимо четырёх базовых модификаторов, в C# есть две комбинированные связки для тонкой настройки границ между проектами (сборками):

| Модификатор | Внутри своего класса | В наследнике (эта сборка) | В другом классе (эта сборка) | В наследнике (другая сборка) | В другом классе (другая сборка) |
| --- | --- | --- | --- | --- | --- |
| `private` | Да | Нет | Нет | Нет | Нет |
| `private protected` | Да | Да | Нет | Нет | Нет |
| `protected` | Да | Да | Нет | Да | Нет |
| `internal` | Да | Да | Да | Нет | Нет |
| `protected internal` | Да | Да | Да | Да | Нет |
| `public` | Да | Да | Да | Да | Да |

### Модификатор `file` для локальных типов (C# 11+)

Если вам нужен вспомогательный класс или структура, который используется только внутри одного конкретного `.cs`-файла и не должен «засорять» подсказки автодополнения в остальном проекте, можно объявить его с модификатором `file`:

```cs
file class StringHelper
{
    public static string Clean(string s) => s.Trim();
}

```

### Тестирование `internal`-кода и рефлексия

Модификаторы доступа проверяются компилятором и средой CLR при обычном выполнении кода, но не являются криптографической защитой:

* **Для юнит-тестов:** чтобы отдельный тестовый проект мог проверять скрытые `internal`-классы, в основной проект добавляют атрибут `[assembly: InternalsVisibleTo("MyProject.Tests")]`.
* **Рефлексия (`System.Reflection`):** с помощью класса `Type` и флага `BindingFlags.NonPublic` программа технически способна прочитать даже `private`-поле во время выполнения, поэтому хранить в закрытых полях реальные пароли или ключи безопасности в открытом виде нельзя.
