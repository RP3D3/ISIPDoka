# Замыкания (Closures): захват внешних переменных

Как лямбда-выражение запоминает локальные переменные из внешнего метода, даже когда сам метод уже завершил работу, и почему захват счётчика цикла `for` приводит к неожиданным ошибкам?

Когда лямбда-выражение обращается к локальной переменной или параметру окружающего метода, возникает **замыкание** (*closure*). Обычно локальные переменные живут на стеке и уничтожаются при выходе из метода, но компилятор C# обходит это ограничение: он незаметно оборачивает захваченную переменную в специальный скрытый класс (*display class*) в управляемой куче (*Heap*). Благодаря этому переменная продолжает жить столько, сколько существует сам делегат, а любые её изменения внутри или снаружи лямбды видны обеим сторонам.

## Механика и особенности замыканий

| Особенность | Как работает под капотом | Практический эффект |
| --- | --- | --- |
| **Захват по ссылке, а не по значению** | Лямбда хранит ссылку на общую ячейку памяти, а не копирует значение в момент создания | Изменение внешней переменной после создания лямбды повлияет на результат её вызова |
| **Продление жизни в куче (*Heap*)** | Компилятор выносит захваченную переменную со стека в поле скрытого объекта в куче | Переменная остаётся доступной даже после завершения работы внешнего метода |
| **Ловушка счётчика цикла `for**` | В цикле `for` создаётся одна переменная-счётчик на все проходы | Все созданные внутри цикла лямбды увидят финальное значение счётчика после окончания цикла |
| **Запрет замыканий (`static` лямбда)** | Модификатор `static` перед лямбдой запрещает обращение к внешнему контексту | Гарантирует отсутствие скрытых выделений памяти в куче (защита от случайных замыканий) |

## Пример кода

```csharp
using System;
using System.Collections.Generic;

class Program
{
    static void Main()
    {
        // 1. Продление жизни переменной: локальная переменная current продолжает жить в куче
        Func<int> counter = CreateCounter(startFrom: 10);
        Console.WriteLine($"Вызов 1: {counter()}"); // 11
        Console.WriteLine($"Вызов 2: {counter()}"); // 12

        // 2. Захват по ссылке: лямбда видит актуальное значение переменной на момент вызова
        int factor = 2;
        Func<int, int> multiply = x => x * factor;
        factor = 5; // Меняем переменную ПОСЛЕ создания лямбды
        Console.WriteLine($"\nРезультат с учётом нового factor: {multiply(4)}"); // 20, а не 8

        // 3. Ловушка цикла for и её исправление через локальную копию
        List<Action> brokenActions = new List<Action>();
        List<Action> fixedActions = new List<Action>();

        for (int i = 0; i < 3; i++)
        {
            // ❌ Все лямбды захватывают одну общую переменную i, которая в конце станет равна 3
            brokenActions.Add(() => Console.Write($"{i} "));

            // ✅ Создаём новую локальную переменную на каждой итерации цикла
            int currentIndex = i;
            fixedActions.Add(() => Console.Write($"{currentIndex} "));
        }

        Console.Write("\nЦикл for без копии: ");
        foreach (Action action in brokenActions) action(); // Выведет: 3 3 3

        Console.Write("\nЦикл for с копией:  ");
        foreach (Action action in fixedActions) action();  // Выведет: 0 1 2
        Console.WriteLine();

        // ❌ Ошибка компиляции (CS8820): static-лямбда запрещает захват внешней переменной factor
        // Func<int, int> strictMultiply = static x => x * factor;
    }

    static Func<int> CreateCounter(int startFrom)
    {
        int current = startFrom;
        // После выхода из CreateCounter переменная current не удалится, а останется жить внутри делегата
        return () => ++current;
    }
}

```

## Важные нюансы

* **Скрытое выделение памяти в куче:** при создании замыкания компилятор генерирует вспомогательный класс с именем вида `<>c__DisplayClass`, превращая локальные переменные в его поля. В обычном коде это незаметно, но в критичных к производительности циклах (например, в игровом движке или сетевом парсере) частые замыкания создают лишнюю работу для сборщика мусора (*Garbage Collector*).
* **Разница между циклами `for` и `foreach`:** в классическом `for (int i = 0; ...)` переменная `i` объявляется один раз перед началом цикла, поэтому все лямбды делят одну ячейку памяти. В цикле `foreach (var item in list)` начиная с C# 5 компилятор автоматически создаёт новую переменную на каждом шаге, поэтому в `foreach` ловушка замыкания не возникает.
* **Защита от случайного захвата через `static` (C# 9+):** если нужно гарантировать, что анонимная функция не захватит внешние переменные (и тем самым не удержит в памяти крупный объект вроде окна или коллекции), добавьте перед ней слово `static` — попытка обратиться к внешней переменной вызовет ошибку компиляции `CS8820`.
* **Связь с теорией и следующей темой:** перенос переменных со стека в кучу напрямую связан с моделью памяти .NET из теоретического раздела (*Стек и куча — Stack & Heap*), а в следующей карточке мы перейдём к событиям и разберём, как ключевое слово `event` защищает делегаты от внешнего вмешательства (*События — event*).
