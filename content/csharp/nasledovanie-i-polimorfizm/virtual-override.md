# virtual и override: переопределение поведения

Как заставить классы-наследники выполнять одно и то же действие по-своему и вызывать нужную версию метода даже при работе через переменную базового типа?

Чтобы разрешить дочерним классам менять логику унаследованного метода, в базовом классе его помечают модификатором `virtual` (виртуальный), а в наследнике переопределяют с помощью `override`. Этот механизм обеспечивает **динамический полиморфизм**: даже если объект наследника хранится в переменной родительского типа, среда выполнения во время работы программы сама определит реальный тип объекта в куче (*Heap*) и вызовет именно его переопределённый метод.

## Сравнение способов работы с методами в иерархии

| Механизм | Ключевые слова | Какой метод сработает через переменную родителя | Когда применять |
| --- | --- | --- | --- |
| **Обычный метод** | Без модификаторов | Метод родительского класса | Когда поведение строго фиксировано и не должно меняться в наследниках |
| **Переопределение** | `virtual` в родителе + `override` в наследнике | Переопределённый метод реального объекта-наследника | Когда у родителя есть базовая логика по умолчанию, но наследники могут её заменить или дополнить |
| **Сокрытие метода** | `new` перед методом в наследнике | Старый метод родительского класса (статическое связывание) | Только в редких случаях совместимости, когда нужно перекрыть невиртуальный метод чужого класса |

## Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        // Храним разные объекты-наследники в общем массиве базового типа Notification
        Notification[] channels =
        {
            new Notification(),
            new EmailNotification(),
            new SmsNotification()
        };

        // Полиморфный вызов: для каждого объекта сработает его собственная версия Send()
        foreach (Notification channel in channels)
        {
            channel.Send("Ваш заказ готов к выдаче");
        }
    }
}

class Notification
{
    // virtual: разрешаем классам-наследникам переопределить поведение по умолчанию
    public virtual void Send(string message)
    {
        Console.WriteLine($"[Система]: {message}");
    }
}

class EmailNotification : Notification
{
    // override: полностью заменяем реализацию базового метода
    public override void Send(string message)
    {
        Console.WriteLine($"[Email-письмо]: {message}");
    }
}

class SmsNotification : Notification
{
    // override + base: дополняем базовую логику родителя своими действиями
    public override void Send(string message)
    {
        base.Send(message);
        Console.WriteLine($"[SMS-дубль на телефон]: {message}");
    }
}

```

## Важные нюансы

* **Ловушка сокрытия метода через `new` (`CS0108`):** если объявить в наследнике метод с тем же именем, что и у родителя, но забыть слово `override`, компилятор выдаст предупреждение `CS0108` и создаст *новый независимый метод*, скрывающий родительский. При обращении через переменную базового типа полиморфизм не сработает — выполнится старый метод родителя.
* **Расширение вместо полной замены через `base`:** внутри `override`-метода можно вызвать `base.MethodName()`, чтобы сохранить стандартную логику базового класса и добавить к ней дополнительные шаги до или после.
* **Правила сигнатуры и блокировка (`sealed override`):** переопределяемый метод обязан в точности повторять имя, параметры, возвращаемый тип и модификатор доступа родительского `virtual`-метода. Модификатор `virtual` нельзя сочетать с `private` или `static`, а связка `sealed override` позволяет запретить дальнейшее переопределение метода в следующих поколениях наследников.
* **Связь с теорией и соседними темами:** работа с разными наследниками через единый базовый интерфейс — прямое воплощение *полиморфизма* и *принципа подстановки Лисков (LSP)*, а если базовому классу вообще не нужна реализация по умолчанию, вместо `virtual` используют `abstract` (см. теоретический раздел: *Полиморфизм* и карточку *Абстрактные классы*).
