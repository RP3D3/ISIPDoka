# StackTrace и отладка: диагностика сбоев

Как по тексту ошибки мгновенно найти точную строку кода, с которой началось падение программы, и не упустить необработанные исключения перед закрытием приложения?

Когда в программе возникает исключение, объект `Exception` автоматически собирает подробную диагностическую сводку о сбое. Главный инструмент расследования — свойство `StackTrace` (**трассировка стека**), которое хранит снимок всех активных вызовов методов от точки входа в программу до конкретной строки, выбросившей ошибку. Умение читать `StackTrace` сверху вниз, раскручивать цепочку вложенных исключений через `InnerException` и перехватывать критические сбои через событие `AppDomain.CurrentDomain.UnhandledException` позволяет точно локализовать баг даже без запущенного отладчика.

## Ключевые свойства и инструменты диагностики

| Инструмент | Что возвращает или делает | Зачем используется при отладке |
| --- | --- | --- |
| `ex.Message` | Краткое текстовое описание причины ошибки | Понять *что* произошло (без указания конкретного места в коде) |
| `ex.StackTrace` | Цепочка вызовов методов с именами файлов и номерами строк | Найти *где* именно упала программа (самая верхняя строка — точка сбоя) |
| `ex.InnerException` / `GetBaseException()` | Ссылка на вложенную ошибку или самую глубокую первопричину | Добраться до исходного технического сбоя, если он был обёрнут выше |
| `AppDomain.UnhandledException` | Глобальное событие перед аварийным завершением процесса | Успеть записать необработанное исключение в лог перед падением |

## Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        // 1. Глобальный перехватчик: сработает перед падением, если ошибку нигде не поймали
        AppDomain.CurrentDomain.UnhandledException += (sender, args) =>
        {
            Exception fatal = (Exception)args.ExceptionObject;
            Console.WriteLine($"[КРИТИЧЕСКИЙ СБОЙ]: {fatal}");
        };

        try
        {
            OrderService orderService = new OrderService();
            orderService.ConfirmOrder(orderId: 705);
        }
        catch (Exception ex)
        {
            Console.WriteLine($"Внешняя ошибка: {ex.Message}");

            // 2. GetBaseException() сразу возвращает самую первую ошибку в цепочке InnerException
            Exception rootCause = ex.GetBaseException();
            Console.WriteLine($"Первопричина: {rootCause.GetType().Name} — {rootCause.Message}\n");

            // 3. Полная трассировка стека: верхняя строка указывает на реальное место сбоя
            Console.WriteLine("Трассировка стека первопричины:");
            Console.WriteLine(rootCause.StackTrace);

            // ❌ Плохо: логировать только ex.Message — без StackTrace невозможно найти строку сбоя
            // Console.WriteLine(ex.Message);
        }
    }
}

class OrderService
{
    public void ConfirmOrder(int orderId)
    {
        try
        {
            ReserveStock(orderId);
        }
        catch (TimeoutException ex)
        {
            // Оборачиваем низкоуровневый сбой БД, сохраняя его в InnerException
            throw new InvalidOperationException($"Не удалось подтвердить заказ #{orderId}.", ex);
        }
    }

    private void ReserveStock(int orderId)
    {
        // Имитация сбоя на самом нижнем уровне вызовов
        throw new TimeoutException("Сервер базы данных не ответил за 5000 мс.");
    }
}

```

## Важные нюансы

* **Как читать `StackTrace` (правило верхней строки):** вызовы методов записываются в стеке в обратном порядке — самая верхняя строка (`at OrderService.ReserveStock(Int32 orderId) in Program.cs:line 54`) указывает на точку непосредственного выброса исключения, а строки ниже показывают цепочку методов, которые привели к этому вызову. При чтении пропускайте системные методы `System.*` и ищите первый метод из вашего собственного кода.
* **Всегда логируйте `ex.ToString()`, а не только `ex.Message`:** свойство `Message` содержит лишь одну общую фразу (например, *«Ссылка на объект не указывает на экземпляр объекта»*), по которой нельзя определить место падения. Вызов `ex.ToString()` (или передача самого объекта `ex` в логгер) автоматически выводит тип исключения, сообщение, всю цепочку `InnerException` и полный `StackTrace`.
* **Откуда берутся номера строк и влияние конфигурации `Release`:** имена исходных файлов и номера строк подтягиваются из файлов отладочных символов (`.pdb`). В режиме `Release` JIT-компилятор для ускорения работы может встраивать (*inline*) короткие методы друг в друга, из-за чего промежуточные вызовы иногда исчезают из стека, но точка реальной ошибки всегда сохраняется.
* **Связь со следующей темой:** достоверность `StackTrace` напрямую зависит от использования пустого `throw;` вместо `throw ex;` (см. карточку *Оператор throw*), а в следующей заключительной карточке мы подведём итоги всей группы и разберём цену исключений для производительности (*Исключения и ошибки*).
