# Комментарии (//, /* */)

Как оставить подсказку в коде для себя или напарника, чтобы через месяц не гадать, зачем здесь эта сложная формула?

:::gap

## Кратко

Комментарии — это текстовые заметки прямо внутри файла с кодом, которые компилятор полностью игнорирует при сборке программы. Однострочные (`//`) подходят для коротких пояснений к конкретной строке, а многострочные (`/* */`) позволяют скрыть целый абзац текста или временно «выключить» кусок кода во время отладки. Они никак не влияют на скорость работы программы, но спасают разработчиков от путаницы в сложных местах.

:::gap

## Быстрый пример

Посмотрим, как оформляются однострочные, многострочные и встроенные комментарии:

```cs
// Однострочный комментарий: действует от символов // до конца текущей строки
int maxRetries = 3; // Можно писать сбоку от инструкции

/*
   Многострочный комментарий:
   удобен для длинных пояснений или временного отключения
   сразу нескольких строк кода при проверке гипотез.
*/
int delay = /* встроенный комментарий прямо внутри выражения */ 500;

Console.WriteLine(maxRetries * delay); // 1500

```

:::gap

## Как это работает

Когда вы запускаете сборку проекта, компилятор читает файл сверху вниз и отбрасывает всё, что помечено как комментарий:

1. **Однострочный комментарий (`//`).** Как только компилятор встречает два прямых слэша подряд, он игнорирует весь оставшийся текст до конца этой строки. Код слева от `//` (например, `int maxRetries = 3;`) выполняется как обычно.
2. **Многострочный блок (`/* ... */`).** Символы `/*` открывают зону комментария, а `*/` закрывают её. Всё, что находится между ними — даже если это десятки строк или валидный код на C# — не попадает в итоговую программу.
3. **Вставка внутрь строки (`/* ... */`).** Поскольку многострочный комментарий имеет чёткое начало и конец, его можно вставить даже в середину выражения — компилятор просто вырежет его, как пробел.
4. **Выполнение оставшегося кода.** После очистки всех заметок остаётся только чистый код (`Console.WriteLine(maxRetries * delay);`), который и выводит `1500`.

> [!TIP]
> В Visual Studio, Rider и VS Code не нужно ставить `//` вручную: выделите нужные строки и нажмите `Ctrl + /` (или `Ctrl + K, Ctrl + C`), чтобы закомментировать или раскомментировать блок одной кнопкой.

:::gap

## Грабли и частые ошибки

### 1. Попытка вложить многострочный комментарий внутрь другого

* **Так не скомпилируется:** обернуть в `/* ... */` большой кусок кода, внутри которого уже есть свой блок `/* описание */`. Компилятор закроет комментарий на самом первом встреченном `*/`, а оставшийся хвост воспримет как сломанный синтаксис (ошибка `CS1025` или `CS1002`).
* **Так правильно:** комментировать большие блоки построчно через `//` (горячей клавишей редактора) или временно отключать куски кода директивой `#if false ... #endif`.

### 2. Незакрытый многострочный комментарий

* **Так не скомпилируется:** написать `/* начало заметки` и забыть поставить `*/` в конце. Компилятор «съест» весь остальной код до самого конца файла и выдаст ошибку `CS1035` (конец файла обнаружен, ожидалось `*/`).
* **Так правильно:** следить за парностью символов `/*` и `*/` или использовать `//` для небольших заметок.

### 3. Мёртвый закомментированный код в проекте

* **Так сработает неправильно:** закомментировать старую реализацию метода «на всякий случай» и оставить её в файле. Через пару недель никто не вспомнит, почему код отключён и можно ли его удалять.
* **Так правильно:** смело удалять неиспользуемый код — для хранения истории и отката изменений существует система контроля версий Git.

### 4. Ожидание комментария внутри кавычек

* **Так сработает неправильно:** думать, что запись `string url = "[https://site.ru](https://site.ru)";` обрежется после `//`. Внутри строковых литералов символы `//` и `/* */` считаются обычной частью текста.
* **Так правильно:** помнить, что комментарии работают только вне кавычек.

:::gap

## Под капотом и нюансы

### Этап лексического анализа

Комментарии вообще не доходят до этапа генерации машинного кода или промежуточного языка IL. На самом первом шаге компиляции — **лексическом анализе** (токенизации) — парсер Roslyn заменяет любой комментарий на пустой служебный элемент (*trivia*). Поэтому скомпилированный `.exe` или `.dll` файл с тысячью подробных пояснений весит ровно столько же и работает с той же скоростью, что и файл без единой заметки.

### XML-комментарии для документации (`///`)

В C# существует третий вид комментариев — три прямых слэша `///` перед классом, методом или свойством. Внутри них пишутся специальные XML-теги (`<summary>`, `<param>`, `<returns>`), которые среда разработки превращает во всплывающие подсказки (IntelliSense) при наведении курсора на ваш метод:

```cs
/// <summary>
/// Вычисляет итоговую стоимость с учётом скидки.
/// </summary>
/// <param name="price">Базовая цена товара.</param>
/// <returns>Цена после применения скидки.</returns>
static double ApplyDiscount(double price) => price * 0.9;

```

### Служебные метки `TODO`, `FIXME` и `HACK`

Редакторы кода (Visual Studio, JetBrains Rider, VS Code с расширениями) сканируют однострочные комментарии на наличие специальных слов в начале текста и собирают их в единый список задач по проекту:

| Метка | Назначение |
| --- | --- |
| `// TODO: ...` | Задача, которую нужно доделать позже (отображается в окне *Task List* в IDE) |
| `// FIXME: ...` | Известный баг или недоработка, требующая обязательного исправления |
| `// HACK: ...` | Неочевидный обходной путь, который выглядит странно, но нужен для работы |

> [!NOTE]
> Хороший код отвечает на вопрос **«Что происходит?»**, а хороший комментарий — на вопрос **«Почему сделано именно так?»**. Не стоит писать `int i = 0; // присваиваем i ноль` — такие пояснения только создают визуальный шум.
