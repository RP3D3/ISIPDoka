# Абстрактные классы abstract

Как запретить создание бессмысленного «общего» объекта вроде `new Shape()` или `new Enemy()`, но при этом заставить каждого наследника обязательно реализовать свой расчёт площади или способ атаки?

:::gap

## Кратко

Абстрактный класс (`abstract class`) — это базовый класс-заготовка, экземпляр которого нельзя создать напрямую через `new`, а можно использовать только как основу для наследования. Внутри него можно объединять обычные готовые поля и методы с абстрактными членами (`abstract`), у которых нет тела реализации — только заголовок. Это жёстко обязывает каждый дочерний класс написать собственную логику для таких методов, гарантируя единый интерфейс работы для всех наследников.

:::gap

## Быстрый пример

Создадим абстрактный класс геометрической фигуры `Shape` и два конкретных класса-наследника — `Circle` и `Rectangle`:

```cs
// Shape s = new("Зелёный"); // Ошибка: нельзя создать экземпляр абстрактного класса

List<Shape> shapes = [new Circle(5, "Красный"), new Rectangle(4, 6, "Синий")];

foreach (Shape shape in shapes)
{
    shape.PrintInfo(); // Вызовет общий метод базового класса, который внутри использует override
}

abstract class Shape(string color)
{
    public string Color { get; } = color;

    // Абстрактный метод: тела нет, наследники ОБЯЗАНЫ его переопределить
    public abstract double GetArea();

    // Обычный метод: общая логика, готовая для всех наследников
    public void PrintInfo()
    {
        Console.WriteLine($"{Color} фигура, площадь: {GetArea():F2}");
    }
}

class Circle(double radius, string color) : Shape(color)
{
    public override double GetArea() => Math.PI * radius * radius;
}

class Rectangle(double width, double height, string color) : Shape(color)
{
    public override double GetArea() => width * height;
}

```

:::gap

## Как это работает

При компиляции и выполнении кода среда .NET контролирует полноту реализации наследников и связывает вызовы методов:

1. **Запрет прямого создания (`abstract class Shape`).** Модификатор `abstract` перед классом говорит компилятору: «фигура сама по себе — это слишком общее понятие, создавать можно только конкретные круг или прямоугольник». Попытка написать `new Shape(...)` остановит сборку.
2. **Обязательный контракт без тела (`public abstract double GetArea();`).** У абстрактного метода нет фигурных скобок `{ ... }` — сразу после круглых скобок ставится точка с запятой `;`. Базовый класс не знает формулу площади для абстрактной фигуры, поэтому требует её от потомков.
3. **Готовая общая логика (`PrintInfo()`).** В отличие от интерфейсов старого образца, абстрактный класс умеет хранить обычные свойства (`Color`), конструкторы и полноценные методы (`PrintInfo`). Более того, метод `PrintInfo` спокойно вызывает абстрактный `GetArea()`, зная, что в реальном объекте он точно будет реализован.
4. **Реализация в наследниках (`override`).** Классы `Circle` и `Rectangle` обязаны переопределить `GetArea()` с помощью ключевого слова `override` и предоставить конкретную математическую формулу.

> [!TIP]
> Если дочерний класс сам объявлен как `abstract` (например, `abstract class Polygon : Shape`), он может не реализовывать абстрактные методы родителя, переложив эту обязанность на своих будущих наследников.

:::gap

## Грабли и частые ошибки

### 1. Попытка создать объект абстрактного класса через `new`

* **Так не скомпилируется:** написать `Shape shape = new Shape("Белый");`. Абстрактный класс считается неполным типом, поэтому компилятор немедленно выдаст ошибку `CS0144`.
* **Так правильно:** создавать экземпляры конкретных классов-наследников (`Shape shape = new Circle(3, "Белый");`).

### 2. Забытая реализация абстрактного метода в наследнике

* **Так не скомпилируется:** написать `class Triangle : Shape` и не переопределить `GetArea()` — компилятор остановит сборку с ошибкой `CS0534` (не реализует унаследованный абстрактный член).
* **Так правильно:** реализовать все абстрактные методы и свойства родителя с модификатором `override`.

### 3. Попытка написать тело `{ }` у абстрактного метода или объявить его в обычном классе

* **Так не скомпилируется:** объявить `abstract` метод внутри класса без слова `abstract` (ошибка `CS0513`) или написать для него тело `public abstract void Run() { }` (ошибка `CS0500`).
* **Так правильно:** если у метода есть базовая реализация по умолчанию — использовать `virtual`, а если реализации нет — убирать `{ }` и делать сам класс `abstract`.

### 4. Сочетание `abstract` с `private`, `static` или `sealed`

* **Так не скомпилируется:** написать `private abstract void Calc();` (ошибка `CS0621`), `public static abstract void Calc();` у метода класса (ошибка `CS0112`) или `abstract sealed class Base` (ошибка `CS0502`). Приватный метод не виден наследникам, а `sealed` запрещает наследование, что противоречит самой сути `abstract`.
* **Так правильно:** объявлять абстрактные члены с доступом `public`, `protected` или `internal`.

:::gap

## Под капотом и нюансы

### Как абстрактные классы устроены в IL и CLR

На уровне промежуточного языка IL абстрактный метод является разновидностью виртуального метода (`virtual abstract` / `newslot`), но в таблице виртуальных методов (**MethodTable**) абстрактного класса в его ячейке записан пустой указатель (`null`). Чтобы программа никогда не попыталась вызвать пустой адрес, среда CLR помечает класс флагом `abstract` и запрещает инструкцию `newobj` для создания его экземпляров. При этом конструктор `.ctor` у абстрактного класса существует и исправно вызывается из дочерних классов через цепочку `: base(...)`.

### Абстрактные свойства и индексаторы

Модификатор `abstract` можно применять не только к методам, но и к свойствам или индексаторам — это удобно, когда наследник обязан предоставить определённое значение:

```cs
abstract class Weapon
{
    public abstract int Damage { get; } // Наследник обязан реализовать свойство
}

class Sword : Weapon
{
    public override int Damage => 25;
}

```

### Выбор инструмента: `abstract class` против `virtual` и `interface`

| Критерий | `abstract` метод в `abstract class` | `virtual` метод в обычном классе | `interface` (интерфейс) |
| --- | --- | --- | --- |
| Можно ли создать `new Type()` | **Нет** (только наследников) | **Да** | **Нет** (только классы-реализации) |
| Реализация в базовом типе | Отсутствует (только сигнатура) | Есть (можно использовать как есть) | Обычно отсутствует (контракт) |
| Обязательность `override` в наследнике | **Обязателен** | Необязателен (по желанию) | Обязательна реализация членов |
| Хранение полей и конструкторов | **Да** (полноценное состояние) | **Да** | **Нет** (нельзя хранить поля) |
| Множественное наследование | Нет (только 1 базовый класс) | Нет (только 1 базовый класс) | **Да** (можно реализовать много) |
