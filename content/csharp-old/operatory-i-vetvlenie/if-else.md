# Условная конструкция if / else

Как научить программу выбирать разные сценарии действий: пустить авторизованного пользователя в личный кабинет или показать ошибку входа?

:::gap

## Кратко

Условная конструкция `if / else` позволяет программе принимать решения и выполнять разные ветки кода в зависимости от того, истинно ли заданное условие. Если проверка в круглых скобках даёт `true`, срабатывает первый блок команд, а если `false` — программа переходит к альтернативному сценарию `else` или следующей проверке `else if`. Это основной механизм ветвления, без которого любая программа работала бы как линейный скрипт без реакции на действия пользователя или игровые события.

:::gap

## Быстрый пример

Проверим уровень заряда батареи и выведем подходящее уведомление:

```cs
int battery = 18;

if (battery > 50)
{
    Console.WriteLine("Заряд в норме");
}
else if (battery > 15)
{
    Console.WriteLine("Низкий заряд"); // Сработает эта ветка
}
else
{
    Console.WriteLine("Критически низкий заряд!");
}

```

:::gap

## Как это работает

При выполнении кода среда .NET проверяет условия строго сверху вниз до первого совпадения:

1. **Первая проверка (`if (battery > 50)`).** Программа подставляет значение `18` и проверяет, больше ли оно пятидесяти. Условие даёт `false`, поэтому блок кода внутри первых фигурных скобок полностью пропускается.
2. **Дополнительная проверка (`else if (battery > 15)`).** Поскольку первое условие не сработало, выполнение переходит ко второму. Проверка `18 > 15` возвращает `true` — программа заходит внутрь и печатает `"Низкий заряд"`.
3. **Пропуск остальных веток (`else`).** Как только хотя бы одна ветка сработала, все остальные блоки `else if` и финальный `else` ниже игнорируются. Блок `else` запустился бы только в том случае, если бы все предыдущие проверки вернули `false` (например, при заряде `10`).

> [!TIP]
> Ветка `else` не обязательна: если при ложном условии ничего делать не нужно, просто напишите одиночный блок `if (...) { ... }`.

:::gap

## Грабли и частые ошибки

### 1. Точка с запятой сразу после скобок `if (...) ;`

* **Так сработает неправильно:** написать `if (hasAccess); { GrantAdmin(); }`. Точка с запятой завершает условный оператор пустым действием, из-за чего код в фигурных скобках выполнится **всегда**, независимо от проверки.
* **Так правильно:** никогда не ставить `;` после закрывающей круглой скобки условия.

### 2. Отказ от фигурных скобок в многострочном блоке

* **Так сработает неправильно:** написать две команды без `{ }` с визуальным отступом: `if (isLoggedIn) Console.WriteLine("Вход"); LoadProfile();`. В C# (в отличие от Python) отступы не влияют на логику: к `if` относится только первая строка, а `LoadProfile()` запустится даже для гостя.
* **Так правильно:** всегда оборачивать тело `if` и `else` в фигурные скобки `{ }`, даже если там всего одна строка.

### 3. Одинарное `=` вместо `==` при проверке `bool`

* **Так сработает неправильно:** написать `if (isReady = true)` — присваивание вернёт `true`, перезапишет переменную и всегда откроет ветку.
* **Так правильно:** писать `if (isReady)` без сравнения с `true` или использовать двойное равно `==` для других типов.

### 4. Неправильный порядок условий в цепочке `else if`

* **Так сработает неправильно:** сначала проверить `if (score >= 50)`, а ниже `else if (score >= 90)`. При значении `95` сработает первое же условие `>= 50`, и до проверки `>= 90` программа никогда не дойдёт.
* **Так правильно:** расставлять проверки от самых строгих и узких условий к более общим.

:::gap

## Под капотом и нюансы

### Инструкции перехода и предсказание ветвлений

На уровне промежуточного языка IL и машинного кода никакого `if / else` нет — компилятор превращает их в условные переходы (`brfalse`, `brtrue`, `bgt`) и метки. Если условие ложно, процессор просто перепрыгивает через блок инструкций к метке `else`.

Современные процессоры используют блок предсказания переходов (*Branch Predictor*), заранее угадывая, какая ветка сработает чаще. Если ветка предсказывается стабильно (например, защита от редкой ошибки), выполнение занимает доли наносекунды, а при хаотичном чередовании `true` и `false` процессор вынужден сбрасывать конвейер вычислений.

### Паттерн «Ранний возврат» (Guard Clauses)

Глубокая вложенность `if` внутри `if` (так называемый «код-лесенка») резко усложняет чтение. В методах лучше отсекать неподходящие случаи сразу в начале через `return`:

```cs
// Плоские защитные проверки (Guard Clauses) вместо глубокой вложенности
void ProcessOrder(Order? order)
{
    if (order is null) return;
    if (!order.IsPaid) return;

    // Основная логика без лишних отступов
    Console.WriteLine("Заказ отправлен в сборку");
}

```

### Проверка типа и объявление переменной прямо в `if`

В современном C# оператор `is` внутри условия позволяет одновременно проверить объект на `null` или нужный тип и сразу создать локальную переменную для работы внутри блока:

```cs
object data = "Привет";
if (data is string text && text.Length > 3)
{
    Console.WriteLine(text.ToUpper()); // Переменная text уже имеет тип string
}

```

### Выбор инструмента для ветвления

| Конструкция | Когда лучше использовать |
| --- | --- |
| `if / else if / else` | Сложные условия с `&&`, `\|\|`, диапазонами и разными переменными |
| Тернарный оператор `?:` | Короткий выбор одного из двух значений прямо при присваивании |
| `switch` / `switch`-выражение | Сравнение одной переменной с набором конкретных значений или шаблонов |
