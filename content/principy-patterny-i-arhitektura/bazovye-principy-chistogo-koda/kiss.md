# Принцип KISS: делай проще

Почему простые и прямолинейные решения работают надёжнее «хитрых» конструкций и как не усложнять код без необходимости?

**KISS** (*Keep It Simple, Stupid* — «делай проще») — принцип проектирования, утверждающий, что большинство систем работают лучше всего, когда остаются простыми, а не усложнёнными. Хороший код пишется не для демонстрации редких трюков языка, а так, чтобы любой разработчик (включая самого автора через полгода) мог прочитать и понять его за несколько секунд.

### Сравнение подходов

| Критерий | Переусложнённый код | Простое решение (KISS) |
| --- | --- | --- |
| **Читаемость** | Требует расшифровки вложенных условий и запутанных формул | Логика читается сверху вниз как обычный текст |
| **Поиск ошибок** | Сложно понять, на каком шаге данные пошли не так | Причина сбоя видна сразу при беглом просмотре |
| **Скорость доработки** | Страшно трогать: правка в одном месте ломает другое | Легко изменить или заменить отдельный шаг |
| **Подход к задаче** | Лишние уровни абстракции и «умные» однострочники | Прямое решение текущей задачи понятными инструментами |

### Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        Console.WriteLine($"Оценка (сложно): {GetGradeClever(82)}");
        Console.WriteLine($"Оценка (просто): {GetGradeSimple(82)}");
    }

    // ❌ ПЛОХО: «умный» вложенный тернарный оператор в одну строку — тяжело читать и править
    static string GetGradeClever(int score)
    {
        return score >= 90 ? "Отлично" : score >= 75 ? "Хорошо" : score >= 60 ? "Удовлетворительно" : "Незачёт";
    }

    // ✅ ХОРОШО: простая линейная проверка с ранним возвратом (читается мгновенно)
    static string GetGradeSimple(int score)
    {
        if (score >= 90) return "Отлично";
        if (score >= 75) return "Хорошо";
        if (score >= 60) return "Удовлетворительно";

        return "Незачёт";
    }
}

```

### Важные нюансы

* **Простота — это читаемость, а не минимум строк:** сжатие пяти понятных строк в одну запутанную формулу с вложенными операторами нарушает KISS. Код пишут один раз, а читают десятки раз.
* **Не усложняйте на старте:** не стройте сложную иерархию классов и паттернов для задачи, которая решается одним простым методом или словарём. Усложнять архитектуру стоит только тогда, когда простого решения реально перестаёт хватать.
* **Разбивайте крупные задачи на мелкие шаги:** если метод разросся на сотню строк и требует комментариев к каждому блоку, разделите его на несколько небольших методов с понятными именами.
* **Практическая реализация:** для упрощения громоздких условий и цепочек проверок используйте ранний выход через `return` и разбиение логики на отдельные подпрограммы (см. раздел языка: *Возврат результата из метода*).
