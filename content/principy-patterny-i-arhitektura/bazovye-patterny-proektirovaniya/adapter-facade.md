# Паттерны Адаптер и Фасад: стыковка и упрощение

Как подружить два несовместимых модуля без переписывания чужого кода и как спрятать запутанную работу десятка классов за одной простой кнопкой?

**Адаптер** (*Adapter*) и **Фасад** (*Facade*) — это структурные паттерны проектирования, которые используют классы-обёртки для наведения порядка в связях между модулями, но решают разные задачи. **Адаптер** работает как переходник для розетки: он переводит вызовы одного интерфейса в формат, понятный другому классу. **Фасад** работает как панель управления: он объединяет сложную подсистему из множества классов и предоставляет к ней простой и понятный вход.

### Сравнение паттернов

| Критерий | Адаптер (*Adapter*) | Фасад (*Facade*) |
| --- | --- | --- |
| **Главная задача** | Сделать так, чтобы несовместимые по интерфейсу классы могли работать вместе | Спрятать сложную подсистему за одним простым и удобным интерфейсом |
| **Аналогия из жизни** | Переходник с американской плоской вилки на европейскую розетку | Кнопка «Запустить кино» на пульте, которая сама включает ТВ, звук и гасит свет |
| **Масштаб работы** | Обычно оборачивает один конкретный класс или внешнюю библиотеку | Охватывает целую группу взаимосвязанных классов и сервисов |
| **Интерфейс на выходе** | Подстраивается под уже существующий интерфейс, который ждёт программа | Создаёт новый упрощённый интерфейс специально для удобства клиента |

### Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        // 1. АДАПТЕР: подключаем старый или внешний сервис через нужный программе интерфейс
        ILogger logger = new LegacyLoggerAdapter(new LegacyFileWriter());
        logger.Log("Приложение запущено");

        // 2. ФАСАД: запускаем сложную цепочку действий одним простым вызовом
        ComputerFacade computer = new ComputerFacade();
        computer.StartComputer();
    }
}

// --- ПРИМЕР АДАПТЕРА ---

// Интерфейс, с которым привыкла работать наша программа
interface ILogger
{
    void Log(string message);
}

// Сторонний или устаревший класс с другим названием метода и лишними параметрами
class LegacyFileWriter
{
    public void WriteTextToDisk(string text, int severityLevel) =>
        Console.WriteLine($"[Файл, уровень {severityLevel}] {text}");
}

// Адаптер: оборачивает чужой класс и переводит вызов в понятный ему формат
class LegacyLoggerAdapter : ILogger
{
    private readonly LegacyFileWriter _writer;

    public LegacyLoggerAdapter(LegacyFileWriter writer)
    {
        _writer = writer;
    }

    public void Log(string message) => _writer.WriteTextToDisk(message, 1);
}

// --- ПРИМЕР ФАСАДА ---

class Cpu { public void Freeze() => Console.WriteLine("Процессор: сброс регистров."); }
class Memory { public void Load() => Console.WriteLine("Память: загрузка ядра ОС."); }
class HardDrive { public void ReadBootSector() => Console.WriteLine("Диск: чтение загрузочного сектора."); }

// Фасад: скрывает сложный порядок запуска компонентов за одним простым методом
class ComputerFacade
{
    private readonly Cpu _cpu = new Cpu();
    private readonly Memory _memory = new Memory();
    private readonly HardDrive _drive = new HardDrive();

    public void StartComputer()
    {
        _cpu.Freeze();
        _drive.ReadBootSector();
        _memory.Load();
        Console.WriteLine("Компьютер готов к работе!");
    }
}

```

### Важные нюансы

* **Главное отличие на практике:** Адаптер *меняет форму* интерфейса, чтобы состыковать два готовых модуля (подгоняет под существующий контракт), а Фасад *уменьшает сложность*, создавая новый простой интерфейс поверх громоздкой системы.
* **Фасад не запрещает доступ к деталям:** хороший фасад упрощает самые частые сценарии работы, но при необходимости опытный разработчик всё равно может обратиться к внутренним классам подсистемы напрямую.
* **Риск превращения Фасада в «божественный объект»:** не пытайтесь впихнуть в один фасад управление всей программой целиком — если подсистем несколько (например, звук, графика и сеть), для каждой лучше завести свой компактный фасад (помните о *SRP*).
* **Практическая реализация:** оба паттерна строятся на базе *композиции* — обёртка хранит ссылки на внутренние объекты в полях и делегирует им выполнение работы (см. раздел принципов: *Наследование против композиции* и раздел языка: *Интерфейсы*).
