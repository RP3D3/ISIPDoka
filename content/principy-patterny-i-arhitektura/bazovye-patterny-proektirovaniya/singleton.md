# Паттерн Одиночка: единая точка доступа

Как гарантировать, что у класса во всей программе будет существовать строго один экземпляр, и почему бесконтрольный глобальный доступ легко превращает архитектуру в запутанный клубок?

**Одиночка** (*Singleton*) — это порождающий паттерн проектирования, который гарантирует существование ровно одного экземпляра класса на всю программу и предоставляет к нему глобальную точку доступа. Для этого конструктор класса закрывают от внешнего вызова (`private`), а сам объект хранят внутри статического поля, выдавая его через общее свойство или метод.

### Зачем применяют и чем опасен для архитектуры

| Аспект | Зачем используют (Плюсы) | Почему портит архитектуру (Риски) |
| --- | --- | --- |
| **Создание объекта** | Запрещает плодить лишние копии общих ресурсов (например, конфигурации приложения) | Класс берёт на себя две роли сразу: свою задачу и контроль создания (нарушение SRP) |
| **Доступ из кода** | Объект легко вызвать из любой точки программы без передачи через параметры | Порождает скрытые зависимости: по заголовку метода не видно, что он обращается к глобальному объекту |
| **Состояние данных** | Все модули читают и обновляют одно общее состояние | Превращается в глобальную переменную: любой участок кода может незаметно перезаписать данные |
| **Тестирование и замена** | Не нужно пробрасывать ссылку через цепочку промежуточных классов | Нельзя легко подменить объект на тестовую заглушку из-за жёсткой привязки к имени класса |

### Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        // ❌ Нельзя создать новый экземпляр напрямую из-за закрытого конструктора:
        // AppSettings bad = new AppSettings(); // Ошибка компиляции!

        // ✅ Получаем единственный общий экземпляр через единую точку доступа
        AppSettings firstLink = AppSettings.Instance;
        AppSettings secondLink = AppSettings.Instance;

        firstLink.Theme = "Тёмная";

        // Обе переменные указывают на один и тот же объект в памяти
        Console.WriteLine($"Тема через вторую ссылку: {secondLink.Theme}");
        Console.WriteLine($"Это один и тот же объект: {ReferenceEquals(firstLink, secondLink)}");
    }
}

class AppSettings
{
    // Единственный экземпляр хранится внутри самого класса
    private static AppSettings _instance;

    public string Theme { get; set; } = "Светлая";

    // Закрытый конструктор запрещает вызывать new AppSettings() снаружи
    private AppSettings() { }

    // Глобальная точка доступа к единственному экземпляру
    public static AppSettings Instance
    {
        get
        {
            if (_instance == null)
            {
                _instance = new AppSettings();
            }
            return _instance;
        }
    }
}

```

### Важные нюансы

* **Почему Одиночку часто называют антипаттерном:** когда десятки классов напрямую вызывают `AppSettings.Instance` внутри своих методов, программа обрастает невидимыми связями. Перенести такой класс в другой проект или протестировать его отдельно становится крайне трудно.
* **Нарушение принципов SOLID:** класс-одиночка нарушает *принцип единственной ответственности (SRP)*, потому что сам управляет своим жизненным циклом, и *принцип инверсии зависимостей (DIP)*, заставляя код жёстко зависеть от конкретного класса вместо интерфейса.
* **Проблема многопоточности:** при одновременном обращении из нескольких потоков простая проверка `if (_instance == null)` может сработать дважды и создать два объекта — в реальных проектах для этого используют потокобезопасную инициализацию (например, `Lazy<T>`).
* **Чем лучше заменить:** вместо создания Одиночки гораздо чище создать один экземпляр обычного класса при запуске программы и передать его нужным модулям через конструктор (см. раздел принципов: *Принцип инверсии зависимостей* и раздел языка: *Статические поля и методы*).
