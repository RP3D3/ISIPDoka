# Наследование против композиции

Почему построение сложных цепочек наследования делает код хрупким и как сборка объектов из независимых деталей решает эту проблему?

**Наследование** и **композиция** — два главных способа связать объекты и повторно использовать код. Наследование строит иерархию по принципу **is-a** («является»: *Кошка является Животным*), передавая дочернему классу всё устройство родителя. Композиция собирает сложный объект из готовых деталей по принципу **has-a** («содержит»: *Автомобиль содержит Двигатель*), позволяя менять компоненты без переписывания всей системы.

### Сравнение подходов

| Критерий | Наследование (`is-a` — «является») | Композиция (`has-a` — «содержит») |
| --- | --- | --- |
| **Суть связи** | Дочерний класс расширяет родительский и получает все его поля и методы | Объект включает в себя независимые компоненты и делегирует им работу |
| **Гибкость изменений** | Жёсткая связь: правка в базовом классе способна сломать всех наследников | Высокая: любой компонент легко заменить на другой даже во время работы |
| **Комбинация функций** | Ограничена: обычно нельзя унаследоваться сразу от нескольких родителей | Не ограничена: внутрь объекта можно вложить сколько угодно разных модулей |
| **Когда применять** | Строгая логическая иерархия, где наследник действительно является частным случаем родителя | Повторное использование возможностей и сборка сложного поведения из простых частей |

### Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        // ❌ ПЛОХО (Наследование ради повторного использования кода):
        // Машина не «является» двигателем (нарушение логики is-a) и жёстко к нему привязана
        BrokenCar oldCar = new BrokenCar();
        oldCar.Drive();

        // ✅ ХОРОШО (Композиция — отношение has-a):
        // Машина «содержит» независимые модули (двигатель и навигатор) и делегирует им работу
        Car modernCar = new Car(new Engine(), new Navigator());
        modernCar.Drive("Центральный парк");
    }
}

class Engine
{
    public void Start() => Console.WriteLine("Двигатель запущен.");
}

class Navigator
{
    public void BuildRoute(string destination) => Console.WriteLine($"Маршрут построен: {destination}");
}

// Неправильное наследование: ради метода Start() пришлось унаследовать машину от двигателя
class BrokenCar : Engine
{
    public void Drive()
    {
        Start();
        Console.WriteLine("Машина поехала.");
    }
}

// Правильная композиция: объект собран из самостоятельных компонентов
class Car
{
    private readonly Engine _engine;
    private readonly Navigator _navigator;

    public Car(Engine engine, Navigator navigator)
    {
        _engine = engine;
        _navigator = navigator;
    }

    public void Drive(string destination)
    {
        _engine.Start();
        _navigator.BuildRoute(destination);
        Console.WriteLine("Машина поехала по маршруту.");
    }
}

```

### Важные нюансы

* **Проверка вопросом «является» или «содержит»:** перед созданием наследника проверьте фразу «Б — это А». Утверждение «Менеджер — это Сотрудник» логично (подходит наследование), а «Заказ — это База данных» — грубая ошибка (нужна композиция).
* **Проблема хрупкого базового класса:** в глубоких деревьях наследования (3–4 уровня вложенности) любое изменение в родительском классе способно непредсказуемо сломать поведение дальних потомков.
* **Золотое правило архитектуры:** «Предпочитайте композицию наследованию» — собирайте сложные объекты из небольших специализированных компонентов, а наследование оставляйте только для строгих иерархий типов.
* **Практическая реализация:** в коде наследование задаётся при объявлении класса, а композиция — через хранение других объектов в полях (см. раздел языка: *Наследование классов* и *Поля и конструкторы*).
