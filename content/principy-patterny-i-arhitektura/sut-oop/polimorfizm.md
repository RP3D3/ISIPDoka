# Полиморфизм и слабая связанность

Как научить программу работать с разными объектами через единую команду, избавиться от громоздких проверок типов и добавлять новые возможности без переписывания старого кода?

**Полиморфизм** (буквально «много форм») — это способность разных объектов отвечать на одну и ту же команду своим собственным способом. В паре с ним работает **слабая связанность** (*Loose Coupling*) — принцип проектирования, при котором модули программы общаются не напрямую друг с другом, а через общий контракт (интерфейс или базовый тип), ничего не зная о внутреннем устройстве конкретных исполнителей.

### Сравнение подходов

| Критерий | Жёсткая связанность (без полиморфизма) | Полиморфизм и слабая связанность |
| --- | --- | --- |
| **Обработка разных типов** | Приходится писать длинные цепочки `if-else` или `switch` для каждого типа объекта | Вызывается один общий метод, а объект сам решает, как именно его выполнить |
| **Добавление нового вида** | Нужно лезть в основной код и дописывать новые ветки проверок | Достаточно создать новый класс с тем же контрактом — старый код не трогается |
| **Зависимость модулей** | Главный код жёстко привязан к конкретным классам и их деталям | Код зависит только от общего контракта (абстракции) |
| **Тестирование и замена** | Сложно подменить один компонент другим без поломки соседей | Любой компонент легко заменяется на аналог или тестовую заглушку |

### Пример кода

```csharp
using System;
using System.Collections.Generic;

class Program
{
    static void Main()
    {
        // ❌ ПЛОХО (жёсткая связанность): при добавлении Telegram придётся менять метод SendBad
        SendBad("Email", "Ваш заказ готов");
        SendBad("SMS", "Ваш заказ готов");

        // ✅ ХОРОШО (полиморфизм и слабая связанность): единый контракт INotification
        List<INotification> channels = new List<INotification>
        {
            new EmailNotification(),
            new SmsNotification()
        };

        // Основной код не знает, как именно отправляется сообщение — он просто вызывает Send
        foreach (INotification channel in channels)
        {
            channel.Send("Ваш заказ готов");
        }
    }

    static void SendBad(string channelType, string text)
    {
        if (channelType == "Email")
            Console.WriteLine($"[Email] Отправка письма: {text}");
        else if (channelType == "SMS")
            Console.WriteLine($"[SMS] Отправка сообщения: {text}");
    }
}

// Общий контракт (единая форма взаимодействия)
interface INotification
{
    void Send(string message);
}

class EmailNotification : INotification
{
    public void Send(string message) => Console.WriteLine($"[Email] Отправка письма: {message}");
}

class SmsNotification : INotification
{
    public void Send(string message) => Console.WriteLine($"[SMS] Отправка сообщения: {message}");
}

```

### Важные нюансы

* **Суть контракта:** полиморфизм отвечает на вопрос *«что объект умеет делать»* (например, «отправить сообщение»), скрывая *«как именно он это делает внутри»*.
* **Защита от разрастания условий:** если в проекте встречается один и тот же `if-else` или `switch` по типу объекта в нескольких местах — это главный сигнал заменить ветвления полиморфизмом.
* **Слабая связанность упрощает командную работу:** пока один разработчик пишет основной алгоритм, опираясь на общий интерфейс, другой может параллельно создавать конкретные реализации, не мешая друг другу.
* **Практическая реализация:** в коде полиморфизм и слабая связанность строятся с помощью интерфейсов и переопределения виртуальных методов (см. раздел языка: *Интерфейсы* и *Виртуальные методы и переопределение*).
