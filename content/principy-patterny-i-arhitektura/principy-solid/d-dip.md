# Принцип инверсии зависимостей

Почему главная бизнес-логика программы не должна напрямую зависеть от конкретной базы данных или способа отправки сообщений и как подменять детали без переписывания ядра?

**DIP** (*Dependency Inversion Principle* — принцип инверсии зависимостей, пятая буква **D** в аббревиатуре **SOLID**) состоит из двух правил: **модули верхнего уровня не должны зависеть от модулей нижнего уровня — оба должны зависеть от абстракций**, а **абстракции не должны зависеть от деталей — детали должны зависеть от абстракций**. Проще говоря, главная логика приложения диктует правила через интерфейс, а конкретные базы данных, файлы или сервисы подстраиваются под этот контракт.

### Сравнение подходов

| Критерий | Нарушение DIP (зависимость от деталей) | Соблюдение DIP (зависимость от абстракций) |
| --- | --- | --- |
| **Направление связи** | Бизнес-логика напрямую создаёт и вызывает конкретные низкоуровневые классы | И бизнес-логика, и низкоуровневые классы зависят от общего интерфейса |
| **Замена технологий** | Переход с сохранения в файл на базу данных требует переписывания основной логики | Достаточно написать новый класс под старый интерфейс и передать его снаружи |
| **Тестирование логики** | Невозможно проверить бизнес-правила без реальной базы данных или сети | Вместо реального сервиса легко подставить простую тестовую заглушку |
| **Устойчивость ядра** | Любая поломка или смена библиотеки на нижнем уровне ломает главный код | Ядро приложения изолировано от технических деталей и остаётся стабильным |

### Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        // ❌ ПЛОХО: сервис заказов сам создаёт FileStorageBad внутри себя —
        // нельзя переключиться на базу данных без правки класса OrderServiceBad
        OrderServiceBad badService = new OrderServiceBad();
        badService.PlaceOrder("Ноутбук");

        // ✅ ХОРОШО (DIP): сервис зависит только от абстракции IStorage,
        // а конкретный способ хранения передаётся снаружи через конструктор
        OrderService fileOrderService = new OrderService(new FileStorage());
        fileOrderService.PlaceOrder("Ноутбук");

        OrderService dbOrderService = new OrderService(new DatabaseStorage());
        dbOrderService.PlaceOrder("Клавиатура");
    }
}

// Нарушение DIP: модуль верхнего уровня жёстко привязан к детали (записи в файл)
class FileStorageBad
{
    public void Save(string data) => Console.WriteLine($"[Файл] Сохранено: {data}");
}

class OrderServiceBad
{
    private readonly FileStorageBad _storage = new FileStorageBad();

    public void PlaceOrder(string item)
    {
        Console.WriteLine($"Оформление заказа: {item}");
        _storage.Save(item);
    }
}

// Абстракция (контракт), которой подчиняются и верхний, и нижний уровни
interface IStorage
{
    void Save(string data);
}

// Деталь 1: подстраивается под интерфейс IStorage
class FileStorage : IStorage
{
    public void Save(string data) => Console.WriteLine($"[Файл] Заказ «{data}» записан на диск.");
}

// Деталь 2: легко добавляется без изменения OrderService
class DatabaseStorage : IStorage
{
    public void Save(string data) => Console.WriteLine($"[База данных] Заказ «{data}» сохранён в таблицу.");
}

// Модуль верхнего уровня зависит только от абстракции IStorage
class OrderService
{
    private readonly IStorage _storage;

    // Внедрение зависимости через конструктор (Dependency Injection)
    public OrderService(IStorage storage)
    {
        _storage = storage;
    }

    public void PlaceOrder(string item)
    {
        Console.WriteLine($"Оформление заказа: {item}");
        _storage.Save(item);
    }
}

```

### Важные нюансы

* **Почему зависимость называется «инвертированной»:** в обычном коде главный модуль напрямую обращается к конкретной библиотеке или классу записи в файл. При соблюдении DIP направление переворачивается: главный модуль задаёт свой интерфейс, а конкретный класс вынужден подстраиваться под него.
* **Не путайте DIP и внедрение зависимостей (DI):** *DIP* — это архитектурный принцип (зависеть от абстракций), а *Dependency Injection (DI)* — практический приём передачи готового объекта через конструктор или параметр метода вместо создания его через `new` внутри класса.
* **Итог всего набора SOLID:** все пять принципов работают вместе — *SRP* и *ISP* делят систему на чистые узкие блоки, *LSP* следит за честным поведением наследников, а *OCP* и *DIP* позволяют свободно менять и расширять детали, не трогая ядро программы.
* **Практическая реализация:** передавайте зависимости через параметры конструктора и используйте интерфейсы как тип полей (см. раздел языка: *Интерфейсы* и *Конструкторы класса*).
