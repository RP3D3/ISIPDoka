# Принцип подстановки Барбары Лисков

Почему наследник не должен ломать логику кода, написанного для родительского класса, и как избежать ошибок при построении иерархии типов?

**LSP** (*Liskov Substitution Principle* — принцип подстановки Барбары Лисков, третья буква **L** в аббревиатуре **SOLID**) гласит: **объекты дочерних классов должны без проблем заменять объекты родительского класса, не нарушая правильную работу программы**. Если код ожидает базовый тип (например, «Птица» или «Документ»), любая его разновидность обязана честно соблюдать обещанные правила поведения, а не выбрасывать внезапные ошибки.

### Сравнение подходов

| Критерий | Нарушение LSP (сломанный наследник) | Соблюдение LSP (корректная подстановка) |
| --- | --- | --- |
| **Поведение при замене** | Подстановка наследника вместо родителя вызывает сбой или искажает результат | Наследник работает предсказуемо везде, где ожидается базовый тип |
| **Методы родителя** | Наследник отключает неподходящие методы заглушками или исключениями | Наследник выполняет все действия, заявленные в базовом классе |
| **Проверки в коде** | Приходится проверять конкретный тип объекта через `if (obj is ...)` | Основной код работает с общим базовым типом без исключений для частных случаев |
| **Проектирование иерархии** | Наследование строится по внешнему сходству объектов в реальном мире | Иерархия строится строго по совместимости поведения в программе |

### Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        // ❌ ПЛОХО: Пингвин унаследован от BirdBad, но не умеет летать — программа упадёт при подстановке
        // MakeBirdFly(new PenguinBad()); // Вызовет ошибку NotSupportedException!

        // ✅ ХОРОШО (LSP): базовый класс Bird не обещает полёт всем подряд,
        // а летать умеют только наследники FlyingBird
        ReleaseToSky(new Sparrow());
        // ReleaseToSky(new Penguin()); // Компилятор сразу не даст передать нелетающую птицу
    }

    static void ReleaseToSky(FlyingBird bird)
    {
        bird.Fly();
    }
}

// Нарушение LSP: базовый класс обещает поведение, которое подходит не всем наследникам
class BirdBad
{
    public virtual void Fly() => Console.WriteLine("Птица летит.");
}

class PenguinBad : BirdBad
{
    // Наследник ломает обещание родителя и выбрасывает ошибку вместо нормальной работы
    public override void Fly() => throw new NotSupportedException("Пингвины не умеют летать!");
}

// Правильная иерархия: общий базовый класс содержит только то, что есть у всех птиц
class Bird
{
    public virtual void Eat() => Console.WriteLine("Птица клюёт корм.");
}

class FlyingBird : Bird
{
    public virtual void Fly() => Console.WriteLine("Птица взлетела в небо.");
}

class Sparrow : FlyingBird
{
    public override void Fly() => Console.WriteLine("Воробей быстро полетел.");
}

class Penguin : Bird
{
    public void Swim() => Console.WriteLine("Пингвин плывёт под водой.");
}

```

### Важные нюансы

* **Логика реального мира обманчива в коде:** в биологии пингвин — это птица, а в геометрии квадрат — это прямоугольник. Но если в программе «Птица» обязана летать, а у «Прямоугольника» ширина и высота меняются независимо друг от друга, прямое наследование нарушит LSP.
* **Главный признак нарушения — заглушки и проверка типа:** если в наследнике приходится оставлять метод пустым, выбрасывать ошибку «не поддерживается» или писать в коде `if (item is SpecialChild)`, иерархия спроектирована неверно.
* **Связь с принципом OCP:** соблюдение LSP делает возможным принцип открытости и закрытости — мы можем спокойно подставлять новых наследников в существующий код, не боясь, что они сломают программу.
* **Практическая реализация:** выносите в базовый класс только действительно общие для всех наследников действия, а дополнительные возможности разделяйте через интерфейсы (см. раздел языка: *Наследование классов* и *Виртуальные методы и переопределение*).
