# Принцип открытости и закрытости

Как добавлять новые функции и правила в программу, не переписывая и не ломая старый, уже проверенный код?

**OCP** (*Open/Closed Principle* — принцип открытости и закрытости, вторая буква **O** в аббревиатуре **SOLID**) гласит: **программные сущности (классы, модули, функции) должны быть открыты для расширения, но закрыты для модификации**. Это значит, что при появлении нового варианта поведения мы добавляем новый код (например, отдельный класс), а не лезем править старые работающие файлы.

### Сравнение подходов

| Критерий | Нарушение OCP (правка старого кода) | Соблюдение OCP (расширение новым кодом) |
| --- | --- | --- |
| **Добавление новой функции** | Приходится открывать старый класс и дописывать ветки `if-else` или `switch` | Создаётся новый отдельный класс, реализующий общий контракт |
| **Риск сломать рабочее** | Высокий: любая правка в рабочем коде может внести случайный баг | Минимальный: проверенный старый код вообще не меняется |
| **Тестирование изменений** | Нужно заново проверять всю старую и новую логику целиком | Достаточно протестировать только новый добавленный модуль |
| **Масштабируемость** | Главный класс разрастается до гигантских размеров со временем | Система растёт за счёт подключения независимых модулей |

### Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        // ❌ ПЛОХО: чтобы добавить VIP-скидку, придётся менять уже работающий класс DiscountBad
        DiscountBad oldCalculator = new DiscountBad();
        Console.WriteLine($"Скидка (плохо): {oldCalculator.Calculate("Regular", 1000)} руб.");

        // ✅ ХОРОШО (OCP): расчёт закрыт от изменений, а новые виды скидок добавляются новыми классами
        DiscountCalculator calculator = new DiscountCalculator();
        Console.WriteLine($"Обычный клиент: {calculator.Calculate(new RegularDiscount(), 1000)} руб.");
        Console.WriteLine($"VIP-клиент: {calculator.Calculate(new VipDiscount(), 1000)} руб.");
    }
}

// Нарушение OCP: любое новое правило заставляет лезть внутрь этого класса
class DiscountBad
{
    public decimal Calculate(string customerType, decimal price)
    {
        if (customerType == "Regular") return price * 0.05m;
        if (customerType == "Seasonal") return price * 0.15m;
        // Для добавления "VIP" придётся изменять этот проверенный метод
        return 0;
    }
}

// Общий контракт для любого вида скидки
interface IDiscount
{
    decimal Apply(decimal price);
}

class RegularDiscount : IDiscount
{
    public decimal Apply(decimal price) => price * 0.05m;
}

// Новое поведение добавлено через новый класс без правки существующего кода
class VipDiscount : IDiscount
{
    public decimal Apply(decimal price) => price * 0.20m;
}

// Класс закрыт для модификации: он работает с любым будущим классом IDiscount
class DiscountCalculator
{
    public decimal Calculate(IDiscount discount, decimal price) => discount.Apply(price);
}

```

### Важные нюансы

* **Связь с полиморфизмом:** именно полиморфизм и интерфейсы позволяют закрыть основной код от правок — калькулятор работает с общим контрактом `IDiscount` и ничего не знает о конкретных типах скидок.
* **Не нарушайте YAGNI заранее:** не нужно строить сложные абстракции вокруг каждого простого условия с первой минуты. Закрывайте код от модификаций в тех местах, где новые варианты действительно появляются регулярно (способы оплаты, форматы отчётов, типы доставки).
* **Исправление багов — не нарушение OCP:** правило «закрыто для модификации» относится к добавлению *нового* поведения. Если в старом классе найдена ошибка, её, разумеется, исправляют прямо в нём.
* **Практическая реализация:** для расширения поведения без правки базовой логики используют интерфейсы, абстрактные классы и паттерн «Стратегия» (см. раздел языка: *Интерфейсы* и раздел принципов: *Полиморфизм и слабая связанность*).
