# Принцип единственной ответственности

Почему классы-«комбайны», которые умеют всё сразу, ломаются при любой мелкой правке и как правильно делить обязанности между модулями?

**SRP** (*Single Responsibility Principle* — принцип единственной ответственности, первая буква **S** в аббревиатуре **SOLID**) гласит: **у класса или модуля должна быть только одна причина для изменения**. Если один класс одновременно считает деньги, сохраняет данные в файл и печатает чек на экран, правка внешнего вида чека может случайно задеть финансовую логику.

### Сравнение подходов

| Критерий | Нарушение SRP (класс-«комбайн») | Соблюдение SRP (узкая специализация) |
| --- | --- | --- |
| **Причины для правки** | Несколько: изменился расчёт, формат хранения или способ вывода | Ровно одна: класс меняется только при правке своей задачи |
| **Риск случайных багов** | Высокий: обновление вывода на экран может сломать вычисления | Минимальный: соседние классы изолированы друг от друга |
| **Повторное использование** | Нельзя взять только расчёт без лишнего кода работы с диском и консолью | Любой модуль легко переиспользовать в другой части программы |
| **Читаемость и объём** | Крупные классы на сотни строк с перемешанной логикой | Компактные классы с понятным названием и прозрачной ролью |

### Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        // ❌ ПЛОХО: класс OrderBad отвечает сразу за три разные задачи —
        // расчёт суммы, сохранение в базу и вывод чека в консоль.
        OrderBad badOrder = new OrderBad { TotalPrice = 1500 };
        badOrder.SaveToDatabase();
        badOrder.PrintReceipt();

        // ✅ ХОРОШО (SRP): каждая обязанность вынесена в свой специализированный класс
        Order order = new Order { TotalPrice = 1500 };
        OrderRepository repository = new OrderRepository();
        OrderPrinter printer = new OrderPrinter();

        repository.Save(order);
        printer.Print(order);
    }
}

// Нарушение SRP: три независимые причины для изменения в одном классе
class OrderBad
{
    public decimal TotalPrice;

    public decimal CalculateWithDiscount() => TotalPrice * 0.9m;
    public void SaveToDatabase() => Console.WriteLine("Сохранение заказа в базу...");
    public void PrintReceipt() => Console.WriteLine($"Чек на сумму: {TotalPrice} руб.");
}

// 1. Отвечает ТОЛЬКО за данные заказа и бизнес-правила расчёта
class Order
{
    public decimal TotalPrice;
    public decimal CalculateWithDiscount() => TotalPrice * 0.9m;
}

// 2. Отвечает ТОЛЬКО за сохранение заказа (меняется только при смене хранилища)
class OrderRepository
{
    public void Save(Order order) => Console.WriteLine($"Заказ на {order.TotalPrice} руб. сохранён в базу.");
}

// 3. Отвечает ТОЛЬКО за отображение чека (меняется только при правке формата вывода)
class OrderPrinter
{
    public void Print(Order order) => Console.WriteLine($"Чек к оплате: {order.CalculateWithDiscount()} руб.");
}

```

### Важные нюансы

* **«Одна ответственность» — это не «один метод»:** внутри одного класса может быть пять или семь методов (например, добавить товар, убрать товар, посчитать итог), если все они работают над одной задачей и меняются по одной бизнес-причине.
* **Связь с принципом SoC:** общий принцип разделения ответственности (*SoC*) учит делить программу на логические слои в целом, а *SRP* уточняет это правило для каждого конкретного класса через поиск единой причины для изменений.
* **Защита от дробления до абсурда:** не нужно разбивать связный класс на десяток микроклассов по три строчки, если их методы всегда меняются вместе — излишнее дробление нарушает принцип *KISS*.
* **Практическая реализация:** разделение обязанностей строится через проектирование независимых классов и их объединение с помощью композиции (см. раздел языка: *Классы и объекты* и раздел принципов: *Наследование против композиции*).
