# Принцип разделения интерфейсов

Почему громоздкие интерфейсы заставляют классы реализовывать ненужные методы и как разбиение контрактов на узкие роли делает код чище?

**ISP** (*Interface Segregation Principle* — принцип разделения интерфейсов, четвёртая буква **I** в аббревиатуре **SOLID**) гласит: **клиенты не должны зависеть от методов, которые они не используют**. Вместо одного огромного интерфейса-«комбайна» лучше создать несколько маленьких специализированных контрактов, чтобы каждый класс подключал только те возможности, которые ему действительно нужны.

### Сравнение подходов

| Критерий | Нарушение ISP (интерфейс-«комбайн») | Соблюдение ISP (узкие интерфейсы) |
| --- | --- | --- |
| **Реализация в классах** | Приходится писать пустые заглушки или выбрасывать ошибки для лишних методов | Класс реализует только те методы, которые реально умеет выполнять |
| **Зависимости кода** | Изменение одного метода в общем контракте затрагивает даже те классы, которым он не нужен | Правка одного узкого интерфейса затрагивает только его прямых исполнителей |
| **Понятность роли** | По контракту непонятно, какие действия объект поддерживает на самом деле | Набор подключённых интерфейсов точно описывает реальные возможности класса |
| **Комбинация функций** | Либо реализуешь всё сразу, либо ломаешь контракт | Любой класс свободно собирает нужную комбинацию из маленьких контрактов |

### Пример кода

```csharp
using System;

class Program
{
    static void Main()
    {
        // ❌ ПЛОХО: простой принтер вынужден «уметь» сканировать и отправлять факс из-за толстого интерфейса
        IPrinterBad oldPrinter = new SimplePrinterBad();
        oldPrinter.Print("Договор.pdf");
        // oldPrinter.Scan("Паспорт.jpg"); // Вызовет ошибку NotSupportedException!

        // ✅ ХОРОШО (ISP): интерфейсы разделены — каждый класс реализует только свои реальные возможности
        IPrinter basicPrinter = new SimplePrinter();
        basicPrinter.Print("Договор.pdf");

        MultifunctionDevice mfu = new MultifunctionDevice();
        mfu.Print("Отчёт.docx");
        mfu.Scan("Накладная.png");
    }
}

// Нарушение ISP: слишком широкий контракт заставляет классы реализовывать лишнее
interface IPrinterBad
{
    void Print(string document);
    void Scan(string document);
    void Fax(string document);
}

class SimplePrinterBad : IPrinterBad
{
    public void Print(string document) => Console.WriteLine($"Печать: {document}");
    public void Scan(string document) => throw new NotSupportedException("Этот принтер не умеет сканировать!");
    public void Fax(string document) => throw new NotSupportedException("В этом принтере нет факса!");
}

// Соблюдение ISP: разделение на узкие специализированные контракты
interface IPrinter
{
    void Print(string document);
}

interface IScanner
{
    void Scan(string document);
}

// Простой принтер зависит только от печати
class SimplePrinter : IPrinter
{
    public void Print(string document) => Console.WriteLine($"Печать: {document}");
}

// МФУ подключает сразу несколько нужных контрактов
class MultifunctionDevice : IPrinter, IScanner
{
    public void Print(string document) => Console.WriteLine($"МФУ печатает: {document}");
    public void Scan(string document) => Console.WriteLine($"МФУ сканирует: {document}");
}

```

### Важные нюансы

* **Прямая связь с принципом LSP:** если интерфейс заставляет класс реализовывать неподходящий метод через заглушку или исключение `NotSupportedException`, такой код одновременно нарушает и ISP, и принцип подстановки Барбары Лисков.
* **Проектируйте от потребностей клиента:** разбивайте интерфейсы исходя из того, какие именно действия нужны вызывающему коду (например, модулю отчётов нужен только `IPrinter`, а модулю архивации — только `IScanner`).
* **Не дробите до одного метода без причины:** если два-три метода всегда используются вместе и описывают единую неделимую роль (например, `Read` и `Write` у потока данных), разделять их на разные интерфейсы не нужно.
* **Практическая реализация:** один класс может одновременно реализовывать сразу несколько узких интерфейсов через запятую (см. раздел языка: *Интерфейсы* и раздел принципов: *Полиморфизм и слабая связанность*).
