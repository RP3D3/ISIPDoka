# Лут и таблицы дропа

Лут — это перевод «монстр умер» в «игрок получил награду». Простая случайность
здесь быстро даёт два неприятных результата: либо игрок десять раз не получает
нужный предмет, либо получает легендарку с первого моба и теряет интерес.
Таблица дропа превращает случайность в управляемый процесс, который можно
проверить и сбалансировать.

## Таблица дропа

Минимальная таблица — список записей с весом:

```csharp
public sealed class LootEntry
{
    public string ItemId;
    public int MinCount = 1;
    public int MaxCount = 1;
    public float Weight = 1f;
    public bool Guaranteed;
}
```

Веса не обязаны быть процентами. Важно только их отношение: веса 50 и 30 дают
те же шансы, что 5 и 3. Проценты удобнее для чтения, но при добавлении новой
строки их приходится пересчитывать. Относительные веса такой проблемы не
создают.

Таблицу стоит воспринимать как контент: её можно редактировать без пересборки
кода, валидировать и показывать дизайнеру.

## Гарантированные дропы

Не всё должно быть случайным. Гарантированные записи выпадают всегда и не
участвуют в розыгрыше весов:

```text
Монстр «Гоблин»
├── гарантированно: 5–10 золота
├── гарантированно: квестовый предмет (если квест активен)
└── случайно: один предмет из таблицы оружия
```

Гарантия решает три задачи:

- квест не может «не выпасть»;
- игрок всегда получает базовую валюту;
- сложные награды не конкурируют с обычным лутом.

Гарантированный предмет всё равно может иметь ограничение: например, квестовый
ключ выдаётся только при активном квесте и только один раз.

## Pity и защита от сухого стрика

Если шанс редкого предмета 5%, это не значит, что он выпадет за 20 попыток.
Вероятность не получить его за 20 попыток всё ещё около 36%. Игрок воспринимает
это как «игра сломана».

Мягкие решения:

- **растущий шанс** — после каждой неудачи шанс немного увеличивается;
- **жёсткая гарантия** — на N-й попытке предмет выдаётся принудительно;
- **счётчик pity** — хранится в сохранении и сбрасывается после успеха.

Pity лучше применять к небольшому числу ключевых наград, а не ко всему луту.
Иначе экономика становится слишком щедрой.

## Экономика

Лут связан с экономикой сильнее, чем кажется:

- сколько золота игрок получает в час;
- сколько стоит починка и расходники;
- сколько попыток нужно, чтобы получить апгрейд;
- что происходит с лишними предметами.

Если лут продаётся, цена должна учитывать редкость и пользу. Если лут
разбирается на материалы, нужен сток, иначе инвентарь заполнится мусором.
Полезно считать **ожидаемую ценность** таблицы: сумма `шанс × цена` по всем
записям. Это не заменяет плейтест, но ловит грубые ошибки.

## Валидация таблиц

Ошибка в таблице обычно обнаруживается через час игры. Дешевле проверить её
на загрузке:

- сумма весов больше нуля;
- все `ItemId` существуют в каталоге;
- `MinCount` не больше `MaxCount`;
- нет дубликатов с одинаковым id без причины;
- гарантированные записи не конфликтуют;
- pity-счётчик не отрицательный.

Хорошая практика — вывести в лог итоговые шансы после нормализации. Тогда
дизайнер видит не «вес 30», а «18.7%».

## Частые ошибки

- **Шанс указан в процентах, но сумма не 100.** Одни предметы выпадают чаще,
  другие никогда.
- **Гарантия внутри взвешенного списка.** Она может проиграть по весу и не
  выпасть.
- **Pity не сохраняется.** После перезапуска счётчик обнуляется, и защита
  исчезает.
- **Слишком много валюты.** Игрок перестаёт ценить награды.
- **Лут не учитывает уровень.** На первом уровне падает оружие конца игры.
- **Нет ограничения на количество.** Один моб выдаёт десять легендарок.
